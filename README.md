# Running Tracker

Веб-трекер беговых тренировок: планы подготовки к стартам, журнал пробежек,
импорт данных из Garmin (CSV/FIT), аналитика и ИИ-тренер на внешней LLM.

**Прод:** https://aabramov77.github.io/running-tracker_new/
**Dev-стенд:** Cloudflare Pages (ветка `Dev`, в углу висит бейдж `DEV`)

Приложение многопользовательское: вход через Google, доступ выдаётся
администратором, данные каждого пользователя изолированы. Единственное
исключение — тренер, которого спортсмен выбрал сам: он видит планы и журнал
этого спортсмена, а если спортсмен разрешил, — создаёт и правит его планы.

## Возможности

### Стартовая страница
- Новый посетитель видит описание возможностей и кнопку «Войти через Google»;
  приложение открывается после входа. Новый пользователь попадает «на
  рассмотрение» — страница предупреждает об этом заранее.
- **One Tap** сам предлагает вход только тому, кто уже входил на этом
  устройстве: истёк часовой токен — вход возвращается без лишних кликов.
  После «Выйти» окно не всплывает.
- Вошедший со свежим токеном видит заставку, пока сервер подтверждает доступ,
  а не стартовую страницу.

### Планы тренировок
- **Несколько планов на пользователя** — переключатель на вкладке «План»,
  архивирование, отдельная гонка (название, дата, целевое время, старт плана)
  для каждого плана.
- **Календарь на 7 дней** (Пн–Вс) с подсветкой текущей недели и типа недели
  (развивающая / пиковая / подводка / загрузочная / гонка).
- **План против факта** — колонка «км» с плановым и фактическим объёмом
  недели и отметки в ячейках дней (выполнено / пропущено / вне плана).
  Окно недели берётся из подписи строки, поэтому разметка пн→вс и вс→сб
  работают одинаково. Плановый объём, который не выводится из текста
  («интервалы 6×800», «14–16 км»), показывается как «не меньше N» — и
  процент выполнения у такой недели не выводится вовсе.
- **Конструктор плана** — редактирование недель прямо в таблице, добавление
  недель, версионное сохранение. Правка уходит вместе с версией плана, поверх
  которой сделана: если план за это время изменили с другого устройства,
  тренером или правкой ИИ-тренера, сохранение отклоняется, а план
  перечитывается.
- **История плана** — кто (вы, тренер, ИИ-тренер), когда и с какой причиной
  сохранял недели. Планы, созданные тренером, подписаны в списке.
- **Импорт плана из файла** — CSV или JSON с предпросмотром, предупреждениями
  и возможностью отменить импорт либо сохранить как новый план.
  Формат описан в [docs/plan-import-format.md](docs/plan-import-format.md),
  образцы — в [docs/samples/](docs/samples/).
- **Экспорт плана** в CSV/JSON + скачивание пустого шаблона.
- **Погода и советы к тренировке** (#72) — прогноз на 7 дней по городу из
  профиля на час тренировки и совет к каждому дню: где бежать (улица, манеж,
  дорожка или перенос) и что надеть по зонам. Опасная погода (гроза, ледяной
  дождь, сильный мороз или жара, шквал) уводит в помещение любую тренировку,
  тяжёлая (скользко, ливень, мороз, жара, порывы) — только работу на
  скорости. На компьютере — строка «Погода» под неделей, на телефоне — кратко
  в дне и подробно в листе дня, полный блок — на «Сегодня». Прогноз —
  [Open-Meteo](https://open-meteo.com/), в GCS не пишется.

### Пробежки
- Ручная запись: дата, дистанция, тип тренировки, время, темп, пульс,
  самочувствие, заметки, привязка к плану.
- **Импорт из Garmin CSV** — поддержаны два формата выгрузки (Activities и
  Laps с многострочной шапкой).
- **Импорт из .FIT** — файл разбирается на сервере (`fitparse`), форма
  заполняется автоматически, сохранение — по кнопке. Круги и поминутные
  сэмплы (пульс, темп, высота) хранятся вместе с пробежкой.
- **Детальная карточка пробежки** — графики пульса и темпа по дистанции,
  таблица кругов.
- **Правка и история правок** (#75, #76) — у каждой пробежки и каждого
  старта: правка, скрытие и восстановление — новые версии, прежние значения
  не теряются. «✎ Изменить» в карточке пробежки открывает форму записи с её
  данными (с причиной правки; загруженный FIT заменяет детали), «🕘 История
  правок» показывает версии и что в каждой поменялось. Под журналом —
  «Скрытые пробежки» с кнопкой «Восстановить». Тренеру этого не видно.
- **Калькулятор** — темп по дистанции и времени и обратно, с переносом
  результата в форму.

### Аналитика
- **Журнал** — хронология пробежек с цветовой индикацией темпа, фильтр по
  плану («текущий план» / «все»).
- **Аналитика** — недельный объём план/факт и динамика темпа (Chart.js).
  Плановые столбцы у недель с неточным объёмом бледнее — там нижняя граница.
- **Недельная нагрузка** — по двум осям: **по темпу** (rTSS: темп с поправкой
  на уклон относительно порогового, 100 = час на пороге) и **по пульсу**
  (TRIMP: метод Банистера, а без пульса покоя или пола — по зонам, метод
  Эдвардса). Неделя пн–вс сравнивается с обычной — средним за 4 предыдущие:
  «ниже обычного / в норме / выше обычного / резкий рост». Текущая неделя
  не оценивается, её заменяют скользящие 7 дней. **Цена работы** — пульсовая
  нагрузка на единицу темповой на лёгких и длительных пробежках: растёт при
  усталости, жаре, болезни. В подсказке к неделе — распределение
  интенсивности (лёгкая / средняя / высокая). Считаются все пробежки, а не
  только плана; без пульса или темпа неделя показывается как «не меньше».
  Нагрузка пробежки — в её карточке (у оценки по средним — «≈»).

### ИИ-тренер
- **Диалог, а не разовый запрос.** Спортсмен ведёт с моделью разговор и
  задаёт уточняющие вопросы; разговоры хранятся отдельными разборами, к
  любому можно вернуться. На каждый ход модель получает свежие данные:
  профиль, план и его выполнение, недельную нагрузку по темпу и пульсу с
  ценой работы, 14 последних тренировок, забеги за 2 года, прогноз погоды
  к дням плана (без города и координат) — и свою память.
- **История за год** (#81). Помесячная сводка по всем пробежкам за 12
  месяцев (объём, самая длинная, темп и пульс на лёгких, rTSS и TRIMP,
  тяжёлые тренировки, перерывы) и итоги до 3 прошлых планов: выполнение и
  результат старта. Это фон для тренда, решения на неделю модель принимает
  по нагрузке и выполнению.
- **Память «Что помнит тренер»** (#80). Модель сама записывает то, что
  спортсмен рассказал в разборах, и договорённости: здоровье, обстоятельства,
  предпочтения, решения. Память общая для всех разборов, до 30 фактов. На
  вкладке «ИИ-тренер» её видно целиком: факт можно поправить, скрыть, вернуть
  или добавить свой. Под ответом тренера — строка «📝 Запомнил: …». Каждое
  изменение — новая версия памяти, история — `GET /ai-coach/memory/history`.
- **Разбор выбранной тренировки** — кнопкой в журнале и в карточке пробежки
  или прикрепив пробежку к вопросу. Модель видит, что стояло в плане на этот
  день, круги (темп, пульс, каденс), темп по половинам, HR-drift и время в
  пульсовых зонах; для пробежки без FIT — сводку.
- **Как отвечает.** Строго и по делу, без мотивационной воды; учитывает фазу
  плана, тренд и восстановление, риск травмы ставит выше результата. Разбор
  тренировки и правку плана даёт по разделам («Вывод», «Что видно по данным»,
  «Главная проблема или сильная сторона», «Что делать дальше», «Корректировка
  плана»), на простой вопрос отвечает коротко. Показатели часов, которых нет в
  данных (HRV, training readiness и т. п.), не требует.
- **Правки плана кнопкой.** ИИ предлагает изменения карточкой «было → стало»
  на текущую неделю и три следующие. Сам он план не меняет: «Применить»
  создаёт обычную новую версию плана с причиной «ИИ-тренер: …», прежняя
  остаётся. Предложение устаревает, если план с тех пор изменился.
- **Лимит** — 30 сообщений в сутки на пользователя (у администратора 300):
  ключ у провайдера общий.
- **Провайдеры LLM:** OpenAI, DeepSeek. Ключ задаёт администратор
  во вкладке «Профиль»; хранится в приватном GCS-объекте и никогда не
  возвращается фронту.

### Старты
Отдельный раздел для результатов забегов: название, дата, дистанция
(4,2 км / 5 км / 10 км / полумарафон / марафон), время. Результат можно
поправить (✎ в строке, история правок — в форме правки), скрытые забеги —
восстановить (#76).

### Профиль
- Характеристики спортсмена: ФИО, дата рождения, пол, рост, вес, пульс
  максимальный / ПАНО / покоя, МПК, стаж, обычный объём, доступные для
  тренировок дни, травмы и свободные заметки для тренера.
- Вычисляется автоматически: возраст, ИМТ, оценка HRmax по формуле Танаки
  (если максимальный пульс не измерен) и пульсовые зоны.
- **Пороговый темп** — темп, который держится около часа; по нему считается
  нагрузка по темпу. Не задан — оценивается по лучшему забегу из «Стартов»
  за год (формула Ригеля), подсказка у поля показывает оценку.
- **Пульсовые зоны можно задать вручную** — начало каждой из пяти зон в
  уд/мин, если проценты от максимального пульса не совпадают с вашими.
  Ручные зоны заменяют расчётные во времени в зонах и в контексте ИИ-тренера;
  «Вернуть авторасчёт» возвращает расчёт от максимального пульса.
- **Личные рекорды** подтягиваются из раздела «Старты».
- **Погода и место тренировок** (#72): город для прогноза (поиск по
  названию или «📍 Моё местоположение» с точностью ~1 км), обычное время
  тренировки, дорожка в зале и манеж, если они доступны, и отношение к
  холоду («мёрзну» и «жарко» сдвигают подбор одежды на 3°).
- Профиль — источник контекста для LLM; кнопка «Показать контекст для ИИ»
  показывает данные, которые ИИ-тренер получает на каждый ход диалога.
- Хранится версионно: каждое сохранение — новая версия, поэтому история
  веса и пульсовых показателей копится сама.
- **Мой тренер** — спортсмен выбирает тренера из назначенных администратором
  и может сменить или снять его в любой момент. Переключатель «Тренер может
  создавать и менять мои планы» включён по умолчанию; у нового тренера он
  снова включается, выключенный оставляет тренеру только просмотр.

### Тренер
- Вкладка «Тренер» видна тренеру и спортсмену, у которого тренер выбран.
- **Тренеру:** список спортсменов, выбравших его, с отметкой нагрузки за
  7 дней, и экран спортсмена — таблица плана с план/фактом, недельный график,
  недельная нагрузка, журнал пробежек с деталями (круги, пульс, заметки,
  нагрузка), история плана, погода и советы к дням плана — с городом
  спортсмена, но без координат.
- **Правка планов тренером** (на широком экране, если спортсмен разрешил):
  новый план с карточкой гонки, конструктор недель, карточка гонки, загрузка
  плана из CSV/JSON. Каждое сохранение — новая версия плана с автором
  «тренер»; комментарий к правке и сама правка приходят спортсмену
  сообщением в диалог, из которого можно открыть план. Если спортсмен успел
  изменить план сам, сохранение тренера отклоняется и редактор открывается
  уже со свежим планом.
- **На телефоне** тренер смотрит план спортсмена неделей, как сам спортсмен,
  и правит один день в листе, с необязательным комментарием для спортсмена.
  Если спортсмен успел изменить план, лист показывает, что теперь стоит в
  этом дне; если выключил правку — остаётся только просмотр.
- **Что остаётся за спортсменом:** какой план активный (план тренера
  становится активным, только если других нет) и архив. Журнал пробежек
  тренер не меняет.
- **Чего тренер не видит:** профиль спортсмена (вес, пульс, травмы), старты,
  разборы с ИИ-тренером и пробежки, которые спортсмен скрыл. Нагрузку он
  видит цифрами, без порогового темпа и параметров профиля, по которым она
  посчитана; по rTSS и темпу пробежки порог можно восстановить — это
  осознанно: темп и пульс пробежек тренер и так видит.
- **Диалог** — один на пару тренер–спортсмен. Счётчик непрочитанных на
  вкладке и в списке спортсменов; уведомлений нет, открытый диалог
  обновляется опросом раз в 30 секунд.
- Доступ даёт только сам спортсмен, и снимается он сразу: при смене тренера
  прежний теряет и данные, и диалог, новый начинает с пустого.

### На телефоне
На экране уже 600 px тот же сайт переключается в раскладку приложения —
отдельной сборки и установки нет.
- **Нижняя панель** вместо меню вкладок: Сегодня · План · «+» · Прогресс · Ещё.
  «Прогресс» объединяет журнал и аналитику, остальные разделы — в «Ещё».
- **Сегодня** — тренировка на сегодня, полоса недели с план/фактом,
  нагрузка за 7 дней и последние пробежки. Строка о цене работы появляется,
  только если она отклонилась от обычной больше чем на 10 %. У плана без дат
  тренировка не показывается: неделю пришлось бы угадывать.
- **План** — одна неделя списком дней, стрелки листают недели.
- **Правка дня** — тап по дню открывает лист с текстом тренировки;
  сохранение создаёт новую версию плана. Конструктор недель, импорт и
  экспорт остаются на широком экране.
- **Тренер** — план спортсмена так же неделей, а если спортсмен разрешил
  правку, тап по дню открывает тот же лист; спортсмен получает сообщение о
  правке в диалог.
- **«+»** — лист с загрузкой .fit / .csv, ручным вводом, калькулятором и
  записью результата забега.

### Администрирование
- Вкладка «Пользователи» (видна только админу): список зарегистрировавшихся,
  одобрение и отклонение доступа, назначение и снятие тренеров.
- Новый пользователь после входа попадает в статус «на рассмотрении».
- Роль администратора доступа к чужим данным не даёт.
- `POST /admin/migrate-history` (#75) переносит пробежки и старты всех
  пользователей, записанные до версий, в версии и пересобирает индексы
  `runs.json` / `races.json`. Повторный вызов ничего не переносит — только
  сверяет индексы с версиями.

## Архитектура

```
GitHub Pages (prod) / Cloudflare Pages (dev)
        index.html + app.js + style.css + landing.css
                    ↓  REST + Bearer <Google ID token>
        Cloud Run Function (Python 3.11)
             runs-api          runs-api-dev
                    ↓
        GCS: running-tracker-aabramov77 / …-dev
```

### Модули бэкенда

Зависимости идут в одну сторону, циклов нет:

```
config.py       константы: client id, бакет, лимиты
domain.py       словарь домена: дни недели, подписи, дистанции, рекорды
compliance.py   план против факта: окна недель, разбор планового дня
load.py         недельная нагрузка: rTSS, TRIMP, оценка к обычной, цена работы
history.py      история для ИИ: месяцы за год, итоги прошлых планов
weather.py      прогноз Open-Meteo (кэш в памяти), место и одежда по правилам
llm_prompt.py   сборка текстового промпта из готового контекста
storage.py      GCS, версии, реестр пользователей, разбор FIT, контекст LLM
api.py          проверка токена, таблица маршрутов, хендлеры
main.py         точка входа Cloud Run Function
```

- Фронтенд — vanilla JS без сборки; выбор API-эндпоинта по hostname.
- Авторизация — Google Identity Services (JS-API: кнопки рисуются в
  `[data-gsi-button]` стартовой страницы), бэкенд проверяет ID-токен и
  разграничивает данные по `sub` из токена. Сертификаты Google для проверки
  подписи держатся в памяти инстанса, пока свежи по `Cache-Control`, а ответ
  на предварительный `OPTIONS` браузер помнит час (`Access-Control-Max-Age`).
- Стартовая страница живёт в том же `index.html`; её стили — в `landing.css`,
  чтобы `style.css` оставался стилями приложения.
- Оффлайн — последние данные кэшируются в `localStorage`.

### Структура данных в GCS

```
users/{sub}/
  runs.json                       индекс пробежек: текущие версии (производный)
  races.json                      индекс стартов: текущие версии (производный)
  profile.json                    legacy: гонка/цель до #25
  athlete/manifest.json           текущая версия профиля спортсмена
  athlete/v{N}/profile.json       неизменяемая версия профиля
  plans/index.json                реестр планов
  plans/{plan_id}/manifest.json   текущая версия плана
  plans/{plan_id}/v{N}/plan.json  неизменяемая версия недель; author — кто правил
  runs/{run_id}/manifest.json     текущая версия пробежки и её деталей FIT
  runs/{run_id}/v{N}/run.json     неизменяемая версия пробежки (#75)
  runs/{run_id}/v{N}/activity.fit исходный FIT — в версии, где его приложили
  runs/{run_id}/v{N}/details.json круги и сэмплы — там же
  races/{race_id}/manifest.json   текущая версия старта
  races/{race_id}/v{N}/race.json  неизменяемая версия старта (#75)
  derived/run_hist.json           кэш нагрузки: гистограммы пульса и скорости
                                  по пробежкам — производное от FIT, не
                                  бизнес-запись, поэтому перезаписывается
  advice/v{N}/recommendation.json разовые рекомендации LLM (до #46, только хранятся)
  advice/usage.json               суточный счётчик обращений к LLM
  ai_coach/t/{thread}/thread.json разбор с ИИ-тренером: карточка ветки
  ai_coach/t/{thread}/m/…         реплики разбора: объект на сообщение
  ai_coach/t/{thread}/applied/…   события «правки плана применены»
  ai_coach/t/{thread}/archived.json  событие «разбор скрыт»
  ai_coach/memory/manifest.json   текущая версия памяти ИИ-тренера (#80)
  ai_coach/memory/v{N}/memory.json   неизменяемая версия: факты и что поменялось
  coach_chat/{coach_sub}/m/…      диалог с тренером: объект на сообщение
  coach_chat/{coach_sub}/read/…   отметки «прочитано до»
users/registry.json               реестр: статус, роль, тренер ли, кто тренер,
                                  можно ли тренеру править планы
users/events/…                    журнал изменений реестра (append-only)
config/llm/…                      конфиг и ключ LLM (только админ)
```

Право тренера на чужие данные проверяется в одном месте —
`storage.coach_access` (нет / просмотр / правка планов) — и по реестру,
прочитанному мимо кэша инстанса.

**Данные append-only.** Физического удаления и перезаписи нет: правка — это
новая версия объекта плюс переключение `is_current`, удаление — логический
флаг. Подробности и обоснование — в [CLAUDE.md](CLAUDE.md). Исключение —
производные объекты вроде `derived/run_hist.json` и индексов `runs.json` /
`races.json`: они целиком восстанавливаются из исходных данных и поэтому
перезаписываются (с предусловием по поколению).

**Каждая запись — с предусловием по поколению объекта** (#35), поэтому
одновременные запросы не затирают друг друга. Способов записи три
(`storage.py`): `create_json` — новый неизменяемый объект, `update_json` —
изменяемый объект вроде индекса `runs.json` или реестра (перечитать и повторить, если
его успели изменить), `commit_version` — новая версия сущности: объект версии
с первым свободным номером, затем манифест. Версия, проигравшая гонку за
манифест, остаётся в хранилище незафиксированной: она не удаляется и в
историю не входит. Поэтому номера версий растут, но могут идти с пропусками.
Без предусловия пишутся только временные `tmp/`; это проверяет
`tests/test_write_preconditions.py`.

**Пробежки и старты — сущности с версиями** (#75), как план. Создание,
правка, скрытие и восстановление пишут новую версию (`commit_version`), у
скрытия — `status: DELETED`. Манифест пробежки общий с деталями FIT: в
каждой версии лежит `run.json`, а `details.json` и `activity.fit` — только в
той, где FIT приложили; `run.json` и манифест (`details_object_path`)
ссылаются на текущие детали. `runs.json` и `races.json` — производный
индекс: после каждой версии в него ставится её запись (монотонно — более
новую версию не затереть), а `rebuild_index` собирает его заново по
манифестам. Формат индекса прежний, плюс `version`. `POST /` и
`POST /races` принимают `base_version` (не совпала — `409 run_stale` /
`race_stale`) и `change_reason`; правка скрытой — `409 run_deleted` /
`race_deleted`. История — `GET /runs/{id}/history`, возврат скрытой —
`POST /runs/{id}/restore`, список скрытых — `GET /runs/hidden` (#76; то же
для `/races`): обычное чтение скрытых не отдаёт. Записи до #75 переносит
`POST /admin/migrate-history`, а до миграции — первая же запись этой
сущности.

**Запись недель плана — с оптимистической блокировкой.** `GET /plan?meta=1`
(и `GET /plans/{id}/weeks?meta=1`) отдаёт `{plan_id, version, weeks}`; клиент
возвращает версию в теле записи как `base_version` (для `POST /plan` ещё и
`base_plan_id`). Не совпала с текущей — `409 {"error": "plan_stale"}`, новая
версия не создаётся. Без `?meta=1` и без `base_version` всё работает
по-старому: массив недель и запись без сверки. Запись тренера
(`POST /coach/athletes/{sub}/plans/{id}/weeks`) без `base_version` не
принимается вовсе.

## Разработка

```bash
git checkout Dev        # весь код пишется в Dev, в main — только merge
python -m pytest -q     # 1269 тестов
```

- Тесты не требуют доступа к GCP: `tests/conftest.py` подменяет
  google-cloud-модули и даёт in-memory `FakeBucket`.
- Хук `.githooks/post-commit` прогоняет pytest после каждого коммита.
- Для ручного глубокого прогона есть субагент `deep-tester`
  (`.claude/agents/deep-tester.md`).
- Фронтенд проверяется статически (баланс скобок, отсутствие
  конфликт-маркеров, cache-buster'ы) — Node в окружении нет.
- При изменении `app.js` / `style.css` / `landing.css` поднимайте `?v=N` в `index.html`,
  иначе браузер отдаст старую версию из кэша.

### Деплой

Push в `Dev` → `runs-api-dev` + dev-bucket; push в `main` → `runs-api` +
прод-bucket. Настроено в
[.github/workflows/deploy-cloudrun.yml](.github/workflows/deploy-cloudrun.yml),
аутентификация в GCP — через Workload Identity Federation, без JSON-ключей.
Перед деплоем job `test` прогоняет pytest на Python 3.11: тесты упали —
деплоя нет. Правка только в `tests/` workflow не запускает.
Фронтенд деплоится сам: GitHub Pages из `main`, Cloudflare Pages из `Dev`.

Первоначальная настройка стендов — [docs/env-split-and-cd.md](docs/env-split-and-cd.md),
обоснование выбора инструментов — [docs/env-split-and-cd-decisions.md](docs/env-split-and-cd-decisions.md).
Ручной деплой функции описан в [DEPLOY.md](DEPLOY.md).

Каждая новая фича начинается с issue в
