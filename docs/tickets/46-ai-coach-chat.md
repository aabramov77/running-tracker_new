# #46 — ИИ-тренер: интерактивный разбор тренировок вместо «Корректировки»

- Issue: https://github.com/aabramov77/running-tracker_new/issues/46
- Ветка: `Dev`
- Коммиты: `feat: #46 …` / `fix: #46 …`

## Контекст

Сейчас вкладка «Корректировка» — это одна кнопка: `POST /advise` собирает общий
контекст и получает жёсткий JSON `{assessment, adjustments, warnings}`
([api.py:391](../../api.py), [llm_prompt.py:214](../../llm_prompt.py)). Нельзя ни задать
уточняющий вопрос, ни указать, какую тренировку разобрать, а рекомендации к
плану остаются текстом, который надо переносить руками. Блок «Эвристики»
([app.js:1610](../../app.js)) считает по зашитому темпу 4:44 и не знает цели плана.

Цель — вкладка «ИИ-тренер»: спортсмен ведёт диалог, выбирает тренировку для
разбора и применяет предложенные правки плана кнопкой.

Согласованные решения:

| Вопрос | Решение |
|---|---|
| Структура разговоров | Отдельные разборы (ветки): тренировка / неделя / свободная тема |
| Правки плана | Карточка «было → стало», кнопка «Применить» создаёт новую версию плана |
| Старые блоки | Заменяются целиком; «Итоги недели» — кнопка-подсказка в чате |
| Лимит | 30 сообщений в сутки на пользователя (админ — 300), ключ общий |

Принцип: **один ход = один вызов LLM**, без агентных циклов. Тренировку
выбирает спортсмен, данные подставляет сервер — расход токенов предсказуем.

## Модель данных (GCS, append-only)

Всё в namespace спортсмена, по образцу чата #44 («сообщение = неизменяемый объект»):

```
users/{sub}/ai_coach/t/{thread_id}/thread.json        # создание ветки: id, kind, run_id, plan_id, title, created_at/by
users/{sub}/ai_coach/t/{thread_id}/m/{msg_id}.json    # сообщение (athlete | ai)
users/{sub}/ai_coach/t/{thread_id}/applied/{msg_id}.json  # событие «предложение применено»
users/{sub}/ai_coach/t/{thread_id}/archived.json      # событие логического скрытия ветки
```

- `thread_id` и `msg_id` начинаются со времени → сортировка имён = хронология;
  счётчик сообщений и «последняя активность» берутся из `list_blobs` без скачивания.
- Сообщение ИИ хранит аудит: `provider, model, input/output_tokens,
  llm_config_version, based_on_plan_id, based_on_plan_version, run_ids`,
  и `proposal` (если есть) со снимком «было» по каждой ячейке.
- Ничего не перезаписывается и не удаляется; «скрыть разбор» — отдельный объект-событие.
- Дневной счётчик — существующий `advice/usage.json`
  (`read_advice_usage` / `increment_advice_usage`, [storage.py:1215](../../storage.py)).
- Старые `advice/v*/recommendation.json` остаются в хранилище нетронутыми.

## Бэкенд

### `storage.py`

- **Многоходовой вызов.** `call_llm(..., history=None)` и
  `_call_openai_compatible(..., history=None)`: сообщения =
  `[system] + history + [user]`. Без `history` тело запроса не меняется
  (существующие тесты `test_llm_client.py` остаются зелёными). JSON-режим
  сохраняется; то же для `_call_anthropic`.
- **Общие хелперы идентификаторов.** Из `_chat_ids` / `append_chat_message`
  ([storage.py:1551](../../storage.py)) выделить функции, принимающие префикс и набор
  ролей (монотонное время, случайный хвост); чат #44 становится тонкой обёрткой.
- **Ветки:** `create_ai_thread`, `list_ai_threads` (без архивных),
  `read_ai_thread`, `archive_ai_thread`, `append_ai_message`, `read_ai_messages`
  (параллельная загрузка, как в `read_chat`).
- **Контекст хода:** `build_ai_turn(bucket, sub, thread, history, text, run_id)`:
  - базовый контекст — существующий `build_llm_context`;
  - окно плана: текущая + 3 следующие недели с номерами (нужно, чтобы правки
    были адресуемыми);
  - фокус-тренировки: `thread.run_id` + `run_id` из сообщений окна, максимум 3;
    проверка владения и `deleted` — как в `_run_details_response` ([api.py:298](../../api.py));
  - история: последние 12 сообщений ветки.
- **Предложение:** `clean_proposal(raw, weeks, plan_start, today)` — неделя в
  пределах плана, день из `DAY_FIELDS`, только даты ≥ сегодня (через
  `week_window` / `day_date` из [compliance.py](../../compliance.py)), текст ≤ 200,
  ≤ 14 правок. Невалидное отбрасывается, ответ остаётся.
- **Применение:** `apply_ai_proposal(bucket, sub, thread_id, msg_id, created_by)`:
  маркер `applied/` уже есть → `already_applied`; активный план или его версия
  не совпали с `based_on_*` → `proposal_stale`; иначе копия недель + правки →
  `save_plan_weeks(change_reason="ИИ-тренер: {summary}")` → запись маркера
  `{from_version, to_version, applied_at, applied_by}`.

### `llm_prompt.py`

- `COACH_CHAT_SYSTEM_PROMPT`: роль тренера, правила (не предлагать недоступные
  дни, не ставить диагнозы, честно говорить о нехватке данных, не выдавать
  оценочные значения за измеренные), формат ответа
  `{"reply": "<markdown>", "proposal": null | {"summary", "changes":[{"week","day","text","reason"}]}}`;
  предложение — только по просьбе или при явной необходимости.
- `format_run_focus(run, details, planned_text, profile, derived)`: сводка,
  **что стояло в плане на этот день**, таблица кругов (темп, пульс ср/макс,
  каденс; до 40), HR-drift (`compute_hr_drift`), темп 1-й/2-й половины, время в
  пульсовых зонах (`HR_ZONE_BOUNDS` из [domain.py](../../domain.py), если известен
  или оценён макс. пульс). Сырые сэмплы не отправляются. Без FIT — сводка и
  пометка «детальных данных нет».
- `format_plan_window(weeks, first_idx)` — недели с номерами и днями.
- `format_context_for_llm` переиспользуется как есть.

### `api.py` — маршруты (все для обычного пользователя, только `c.sub`)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/ai-coach/threads` | список разборов + `usage {count, limit}` |
| POST | `/ai-coach/threads` `{kind, run_id?}` | новая ветка (без вызова LLM) |
| GET | `/ai-coach/threads/{tid}` | ветка + сообщения с `proposal_state` (open / applied / stale) |
| POST | `/ai-coach/threads/{tid}/messages` `{text, run_id?}` | ход: LLM → запись пары сообщений |
| POST | `/ai-coach/threads/{tid}/messages/{mid}/apply` | применить предложение |
| POST | `/ai-coach/threads/{tid}/archive` | скрыть разбор |

- Порядок в ходе: лимит → контекст → LLM → **только после успеха** запись
  сообщения спортсмена и ответа ИИ → инкремент счётчика. При сбое в ветке не
  остаётся «висящего» вопроса, текст сохраняется в поле ввода.
- Ошибки LLM — та же раскладка, что в `h_advise_post` (422 отказ, 502
  обрыв/провайдер); вынести в общий хелпер. Ответ не-JSON → весь текст идёт
  как `reply`, без предложения.
- `config.py`: `DAILY_AI_COACH_LIMIT = 30`, `ADMIN_DAILY_AI_COACH_LIMIT = 300`
  вместо `DAILY_ADVISE_LIMIT`.
- `/advise/preview` остаётся (кнопка «Показать контекст для ИИ» в Профиле).
  `GET/POST /advise`, `write_advice_version`, `read_latest_advice` удаляются
  в последней фазе вместе с их тестами.
- Тренер-человек (#44) доступа к разборам не получает: тренерских маршрутов
  на `ai_coach` нет.

## Верификация

1. `pytest` — весь набор зелёный (сейчас 443).
2. Dev-стенд (`running-tracker-new-4ih.pages.dev`, бэкенд `runs-api-dev`;
   localhost войти не может):
   - из журнала «Разобрать с ИИ» на пробежке с FIT → ответ ссылается на круги
     и на то, что стояло в плане в этот день; уточняющий вопрос учитывает
     предыдущий ответ;
   - в том же разборе прикрепить вторую тренировку и попросить сравнить;
   - «Что поменять на следующей неделе» → карточка предложения → «Применить» →
     план показывает новые ячейки, в GCS появилась `plans/{id}/v{N+1}` с
     причиной «ИИ-тренер: …», предыдущая версия на месте;
   - изменить план вручную, вернуться к старому предложению → «Устарело»;
   - список разборов сохраняется после перезагрузки; скрытый разбор пропадает
     из списка, объекты в GCS остаются;
   - невалидный ключ LLM → понятная ошибка, текст остался в поле ввода;
   - счётчик лимита убывает; на исчерпании — 429 и сообщение в интерфейсе.
3. PR `Dev → main` с `Closes #46`.

## Вне рамок

Потоковый вывод ответа, самостоятельный запрос данных моделью (tool calling),
доступ тренера-человека к разборам, откат применённой правки кнопкой (версии
плана сохраняются, вернуть можно вручную), сжатие длинной истории в резюме.
