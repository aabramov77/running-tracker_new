# #75 — История правок пробежек и стартов

- Issue: https://github.com/aabramov77/running-tracker_new/issues/75
- Ветка: `Dev`
- Коммиты: `feat: #75 …`
- PR: `Dev → main`, в теле `Closes #75`
- Статус: план согласован 2026-11-03, реализовано (см. «Отличия от плана»).

## Контекст

После #35 `runs.json` и `races.json` пишутся с предусловием, и одновременные
правки не теряются. Но это по-прежнему изменяемые списки: `POST` с id
существующей пробежки заменяет запись целиком, прежние значения пропадают,
истории нет. Политика хранения ([CLAUDE.md](../../CLAUDE.md)) требует, чтобы
каждая правка и каждое удаление были новой версией. В #35 это вынесено «вне
рамок» в отдельный тикет — этот.

Попутно чинится то, что сейчас теряется при правке: `h_runs_post` собирает
пробежку заново из тела запроса, поэтому `POST` с тем же id без `fit_token`
стирает `details_available`, `max_hr`, `avg_cadence` и т.д. — ссылка на детали
FIT остаётся, а карточка их больше не показывает.

Что есть на проде (листинг бакета, 2026-11-03):

| | |
|---|---|
| пользователей с `runs.json` | 3 |
| пробежек | 197 (скрытых 18), у 182 `details_available` |
| стартов | 26 (скрыт 1), у 2 пользователей |
| `runs/{id}/manifest.json` деталей FIT | 175, все на `v1` |
| объектов в `users/` всего | ~1000 |

UI сейчас пробежки и старты только добавляет и скрывает — формы правки нет.
Правка возможна только через API (`POST` с существующим id).

## Решение

### Модель: сущность на объект с версиями

Пробежка и старт устроены как план и профиль: манифест + неизменяемые версии,
запись — через `commit_version`.

```
users/{sub}/
  runs/{id}/manifest.json        текущая версия пробежки (общий с деталями FIT)
  runs/{id}/v{N}/run.json        неизменяемая версия пробежки
  runs/{id}/v{N}/details.json    круги и сэмплы — только в версии, где приложен FIT
  runs/{id}/v{N}/activity.fit    исходный FIT — там же
  races/{id}/manifest.json       текущая версия старта
  races/{id}/v{N}/race.json      неизменяемая версия старта
  runs.json, races.json          производный индекс текущих версий
```

### Манифест пробежки — общий с деталями FIT

`runs/{id}/manifest.json` уже есть у 175 пробежек и указывает на
`v1/details.json`. Решение — **один манифест на пробежку**: в `v{N}/` всегда
лежит `run.json`, а `details.json` и `activity.fit` — только в той версии, где
к пробежке приложили FIT.

Почему общий, а не отдельный:
- пробежка — одна сущность: один номер версии и одна история. Повторная
  привязка FIT — тоже правка пробежки (меняются `details_available`, `max_hr`
  и др.), и она должна быть в той же истории;
- пробежка с FIT становится одной атомарной версией. Сейчас детали
  фиксируются отдельно, а `runs.json` пишется следом: сбой между записями
  оставляет детали без пробежки;
- с отдельным манифестом в одной папке `v{N}/` лежали бы объекты с разными
  номерами (`run.json` v2 и `details.json` v2 — разные версии разного). Значит,
  отдельному манифесту нужна отдельная папка (`runs/{id}/record/v{N}/`), а это
  вторая история и второй номер.

Новый формат манифеста:

```json
{
  "current_version": 3,
  "gcs_object_path": "users/{sub}/runs/{id}/v3/run.json",
  "details_object_path": "users/{sub}/runs/{id}/v1/details.json",
  "status": "ACTIVE",
  "created_at": "…Z", "created_by": "runner@example.com",
  "change_reason": "…",
  "checksum": "sha256 от run.json"
}
```

`details_object_path` — детали текущей версии: они могут лежать в более ранней
версии, если FIT с тех пор не меняли; `null` — FIT нет. Новый формат
отличается от старого наличием ключа `details_object_path`. В старом
`gcs_object_path` указывает на `details.json`; `read_run_details` понимает оба
формата.

Манифест старта — тот же, без `details_object_path`.

### Payload версии

```json
{
  "id": 1730000000000,
  "version": 3,
  "is_current": true,
  "status": "ACTIVE",
  "created_at": "…Z",
  "created_by": "runner@example.com",
  "author": "athlete",
  "change_reason": "…",
  "supersedes_version": 2,
  "deleted_at": null,
  "deleted_by": null,
  "run": {"date": "…", "dist": 10.0, "type": "easy", "time": "…", "pace": "…",
          "hr": 140, "feel": "good", "notes": "…", "plan_id": "…",
          "details_available": true, "max_hr": 165, "avg_cadence": 172,
          "total_ascent_m": 40, "calories": 600},
  "details_object_path": "…/v1/details.json",
  "fit_object_path": "…/v1/activity.fit"
}
```

У старта вместо `run` — `race: {name, date, dist_label, time}`, без путей FIT.
`author` — `athlete` или `migration` (почту, как и в истории плана, наружу не
отдаём). `supersedes_version` — фактическая основа, как у всех версий после #35.

### Запись

Один писатель на вид сущности (`storage.py`, раздел «Пробежки и старты»),
общий для пробежек и стартов: что меняется, решает `build(текущий payload)`
внутри `claim`, поэтому решение всегда принимается по текущей версии —
манифест пишется с предусловием, и если версию успели сменить,
`commit_version` позовёт `claim` заново.

- **Создание и правка** — `save_run` / `save_race`, вызываются из `POST /` и
  `POST /races`:
  - поля, которые вводит пользователь, — из запроса; поля из FIT и пути к
    деталям — из текущей версии, если не пришёл новый `fit_token`;
  - `plan_id` не пришёл: при правке остаётся прежний, при создании — активный
    план, как сейчас;
  - с `fit_token` в ту же папку `v{N}/` ложатся `details.json` и
    `activity.fit`. `run.json` пишется последним: папка версии, где есть
    `run.json`, всегда полная; любой из объектов уже есть (след сбоя) — номер
    занят, берётся следующий;
  - правка без изменений (повтор запроса после сбоя, двойной клик) новой
    версии не создаёт — возвращается текущая, индекс при этом
    подправляется;
  - правка скрытой пробежки — `409 run_deleted`: сначала восстановить;
  - `base_version` в теле — по желанию, как у плана: не совпал с текущей →
    `409 run_stale` (`race_stale`). Без него — без сверки (так пишет текущий
    фронтенд). `GET /` и `GET /races` отдают `version` в каждой записи.
- **Удаление** — `delete_run` / `delete_race`: новая версия со
  `status=DELETED`, `deleted_at`, `deleted_by`, снимок полей тот же. Повторное
  удаление новой версии не пишет и `deleted_at` не сдвигает (как сейчас).
- **Восстановление** — `restore_run` / `restore_race`: новая версия
  `status=ACTIVE` со снимком полей последней версии. Восстановление активной —
  без записи.

Исключения: `RunStale` / `RaceStale` (подклассы `VersionStale`) и
`EntityDeleted`. `StorageBusy` → 503 `storage_busy`, как после #35.

`upsert_run`, `soft_delete_run`, `upsert_race`, `soft_delete_race`,
`_upsert_entry`, `_soft_delete_entry` удаляются. Перенос FIT из `tmp/` и
`remember_run_hist` переезжают из `attach_fit_details_to_run` в `save_run`.

### Индекс `runs.json` / `races.json`

Формат прежний — список записей той же формы (`deleted`, `deleted_at`), плюс
`version`. Поэтому читатели не меняются: журнал, тренер, выполнение плана,
нагрузка, контекст ИИ-тренера, `find_own_run`.

- После каждой зафиксированной версии запись индекса ставится через
  `update_json`. Монотонно: если в индексе уже версия не младше — ничего не
  пишется. Две правки одной пробежки, чьи записи в индекс пришли в обратном
  порядке, всё равно сходятся на текущей.
- Упал между версией и индексом — индекс отстаёт. Чинится следующей записью
  этой сущности (даже правкой без изменений) или пересборкой.
- **Пересборка** `rebuild_index(bucket, sub, kind)`: манифесты из
  `list_blobs(users/{sub}/runs/)` → текущие payload'ы (параллельно, как
  `_load_json_objects`) → список по id от новых к старым. Индекс поменялся —
  пишется через `update_json`. Записи старого индекса, у которых ещё нет
  версий (до миграции), сохраняются как есть.

### Миграция: явная + страховка при записи

- **Базовая версия** из записи индекса: снимок полей, `status` по
  `deleted`, `deleted_at` из записи, `author: migration`,
  `created_by: auto-migrate`, `change_reason: «перенос из runs.json (#75)»`.
  У пробежки со старым манифестом деталей это `v2` с
  `supersedes_version: 1` и путями деталей и FIT из `v1`; история
  показывает и её, и `v1` («детали FIT»). Пишется через `commit_version` с
  `base_version` = увиденная текущая: если параллельно мигрировал кто-то
  другой — `VersionStale`, второй базовой версии не будет.
- **Явная миграция** — `POST /admin/migrate-history` (только админ): по всем
  пользователям реестра базовые версии для записей без версий, затем
  пересборка индексов; отчёт по пользователям, как у `migrate-legacy`.
  Идемпотентна, повторный вызов — это «проверить и починить индекс».
  223 сущности × ~4 операции — параллельно, секунды.
- **Страховка при записи**: `save_*`, `delete_*`, `restore_*` сначала делают
  базовую версию, если её у сущности ещё нет. Правка в окне между деплоем и
  миграцией не затрёт прежние значения.
- Почему не лениво на чтении (как `migrate_single_plan`): чтение пробежек есть
  у тренера, в нагрузке и в контексте ИИ — тренер писал бы в данные
  спортсмена (в нагрузке #66 этого специально избегали), а первое чтение у
  пользователя со 128 пробежками стало бы медленным. Индекс же читается и до
  миграции.
- Legacy-детали админа (`runs/{id}/` в корне): если у пробежки админа нет
  своего манифеста, перед базовой версией детали копируются, как сейчас в
  `read_run_details` (код выносится в `_copy_legacy_run_details`). На проде
  у всех 55 пробежек админа манифест уже есть, путь оставлен для полноты.
- `migrate_single_plan` привязывает пробежки к перенесённому плану правкой
  `runs.json` — теперь это версии пробежек (`change_reason: «привязка к
  плану (#25)»`), иначе пересборка индекса привязку бы потеряла.

### История правок

`GET /runs/{id}/history` и `GET /races/{id}/history` — от новых к старым, до
50, как у плана (`version_chain` по `list_blobs`):

```json
{"run_id": 1730000000000, "has_more": false,
 "versions": [{"version": 3, "created_at": "…", "author": "athlete",
               "change_reason": "…", "status": "DELETED",
               "fit_attached": false, "run": {…снимок…}}]}
```

`fit_attached` — эта версия принесла новые детали FIT. Версия до #75 (только
`details.json`) — запись с `change_reason: «детали FIT»` и `run: null`.
История доступна и для скрытой пробежки: это явное историческое чтение.
Своих данных — только своих: путь строится из `sub` токена, чужого id просто
нет.

### API (итог)

| Метод | Путь | Что |
|---|---|---|
| `GET` | `/`, `/races` | как было, в записях есть `version` |
| `POST` | `/`, `/races` | создание или правка; `base_version`, `change_reason` по желанию; 409 `run_stale` / `run_deleted` (`race_…`) |
| `DELETE` | `/?id=`, `/races?id=` | ответ прежний `{soft_deleted, deleted_at}` |
| `POST` | `/runs/{id}/restore`, `/races/{id}/restore` | новая активная версия; 404 — нет такой |
| `GET` | `/runs/{id}/history`, `/races/{id}/history` | история версий |
| `POST` | `/admin/migrate-history` | миграция и пересборка индексов (админ) |

Маршруты тренера не меняются: он читает индекс.

### Фронтенд

В этом тикете — без изменений: UI только создаёт и скрывает, а это работает
через те же маршруты с тем же ответом. Форма правки пробежки, «История
правок» в карточке и список скрытых с «Восстановить» — отдельный тикет (см.
«Вне рамок»).

## Отличия от плана

- **Legacy-детали связываются и при создании.** Раньше детали админа из
  корня бакета копировались при первом чтении, если у пробежки не было
  манифеста. Теперь манифест есть у любой пробежки с первой версии,
  поэтому копия делается заранее: при миграции и при создании пробежки под
  id, у которого уже есть детали без версий (legacy у админа или детали,
  зафиксированные до #75 без записи в `runs.json`). Общий код —
  `_details_before_versions`. В `test_security.py` проверка «в namespace
  пользователя ничего не появилось» сужена до копий деталей и FIT: свои
  `run.json` и манифест у пробежки теперь есть всегда.
- `attach_fit_details_to_run` удалена: FIT — часть `save_run`, удаление
  `tmp/` — в `_drop_tmp_fit` (сторож: `TMP_DELETERS`).
- Плохой токен FIT — `FitTokenInvalid` (подкласс `ValueError`): `400` больше
  не отдаётся на любой `ValueError` при записи.
- Причина правки по умолчанию: «создание», «правка», «скрытие»,
  «восстановление»; у миграции — «перенос из runs.json (#75)».
- Правка оставляет запись на месте в индексе (раньше — поднимала наверх);
  пересборка упорядочивает по id от новых к старым. Интерфейс сортирует по
  дате, порядок индекса ему не важен.
- Перенос одиночного плана (#25) привязывает только активные пробежки:
  скрытую правка не трогает (`EntityDeleted`).
- Сверка `base_version` вынесена в `api._base_version` — общая для недель
  плана, пробежек и стартов.

## Вне рамок

- UI: форма правки пробежки и старта, история правок в карточке, список
  скрытых с восстановлением — отдельный тикет.
- История пробежек спортсмена для тренера.
- Правка карточки гонки плана уже пишет события (#60) — не трогаем.
