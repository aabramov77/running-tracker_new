# #32 — Профиль пользователя

- Issue: https://github.com/aabramov77/running-tracker_new/issues/32
- Ветка: `Dev`
- Коммиты: `feat: #32 …`

## Контекст

Приложение ничего не знает о самом бегуне. Рекомендации LLM строятся только на
тренировках, плане и стартах: модель не видит ни возраста, ни пульсовых
показателей, ни ограничений по здоровью, ни доступных для тренировок дней —
и потому даёт советы «в среднем по больнице».

Объект `users/{sub}/profile.json` формально существует, но это **не профиль
спортсмена**: там четыре поля гонки (`race_name`, `race_date`, `target_time`,
`plan_start`), оставшиеся от версии до #25. Сейчас данные гонки живут в плане,
а старый объект нужен ровно в одном месте — `migrate_single_plan()` читает его
при ленивой миграции пользователей, заведённых до #25. Эндпоинт `/profile`
жив, но фронтенд к нему не обращается.

Отсюда план: legacy-объект не трогаем (переименовываем только хелперы, чтобы
имя не врало), `/profile` забираем под настоящий профиль спортсмена.

## Решения

**Вариант A для «шаблона LLM».** Шаблон — это сам профиль: заполненные поля
автоматически собираются в текстовый блок контекста, плюс свободное поле
«от спортсмена» для того, что в поля не укладывается, плюс кнопка
предпросмотра — увидеть ровно то, что уйдёт в модель. Отдельный редактируемый
шаблон с плейсхолдерами (вариант B) отложен: он создаёт класс проблем
«шаблон разъехался с полями» без явной пользы на старте.

**Вкладка «Настройки» → «👤 Профиль».** Настройки ИИ становятся карточкой
внутри профиля. Сейчас не-админ открывает «Настройки» и видит там мёртвую
заглушку «Моя гонка» и записку о том, что настройками занимается
администратор — вкладка называется «Настройки», а настраивать в ней нечего.
После переименования вкладка осмысленна для всех, а нав-бар не растёт до
девяти кнопок (на телефоне он и так тесный).

**Личные рекорды не дублируем.** Берём лучший результат на каждой дистанции
из раздела «Старты». Ручной ввод не заводим: расхождение между разделом
«Старты» и профилем — источник неверного контекста для LLM.

## Хранение

Профиль — бизнес-запись, значит версионно (CLAUDE.md: append-only,
без перезаписи):

```
users/{sub}/athlete/manifest.json      {current_version, gcs_object_path, updated_at}
users/{sub}/athlete/v{N}/profile.json  {version, is_current, created_at, created_by,
                                        change_reason, supersedes_version, profile:{…}}
```

Побочный выигрыш: каждое сохранение — точка во времени, то есть история веса
и пульсовых показателей появляется бесплатно. Эндпоинт истории закладываем
сразу, график динамики — потенциальный отдельный тикет.

Новые построители путей рядом с остальными:

```python
def p_athlete_manifest(sub): return f"{upfx(sub)}athlete/manifest.json"
def p_athlete_ver(sub, v):   return f"{upfx(sub)}athlete/v{v}/profile.json"
```

## Поля

| Группа | Поле | Тип / диапазон |
|---|---|---|
| Личное | `full_name` | текст |
| | `birth_date` | дата, не в будущем, возраст ≤ 100 |
| | `sex` | `""` / `m` / `f` |
| | `height_cm` | 100–250 |
| | `weight_kg` | 30–200 |
| Физиология | `hr_max` | 100–230 |
| | `hr_threshold` (ПАНО) | 80–220, строго меньше `hr_max` |
| | `hr_rest` | 30–120 |
| | `vo2max` | 20–90 |
| Тренировки | `years_running` | 0–70 |
| | `weekly_km_typical` | 0–300 |
| | `sessions_per_week` | 0–14 |
| | `available_days` | подмножество `mon…sun` |
| | `long_run_day` | `""` или один из `mon…sun` |
| Здоровье | `injuries` | текст |
| Свободное | `notes` | текст, «от спортсмена» для тренера |

Пустая строка / `None` = не заполнено; незаполненные поля в контекст LLM
не попадают.

### Вычисляемое (не хранится)

Считает сервер, отдаёт вместе с профилем:

- `age` — из `birth_date`
- `bmi` — из роста и веса
- `hr_max_estimated` — формула Танаки `208 − 0.7 × возраст`, **только если
  `hr_max` не заполнен**
- `hr_zones` — пять зон в % от HRmax (50/60/70/80/90–100)

Оценочные значения помечаются в контексте LLM явно («оценка»), чтобы модель
не приняла прикидку за измерение. Зоны — ориентир, не медицинская
рекомендация.

## API

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/profile` | `{profile, derived, personal_bests, version, updated_at}` |
| POST | `/profile` | валидация → новая версия → тот же объект |
| GET | `/profile/history` | `[{version, created_at, change_reason, weight_kg, hr_max, hr_threshold}]` |
| GET | `/advise/preview` | `{prompt}` — полный текст, который уйдёт в LLM |

Ошибка валидации: `400 {"error": "validation_failed", "fields": {"hr_max": "…"}}`.

`/advise/preview` живёт рядом с `/advise`, потому что показывает именно
контекст рекомендаций целиком (профиль + план + тренировки + забеги), а не
один лишь профиль.

## Контекст LLM

`build_llm_context()` добавляет `profile` (с вычисляемыми) и
`personal_bests`. `format_context_for_llm()` печатает блок первым, до целей:

```
Профиль: М, 47 лет, 182 см, 74 кг (ИМТ 22.3)
Пульс: макс 178, ПАНО 162, покой 48
Опыт: 6 лет, обычный объём 45 км/нед, 4 тренировки
Доступные дни: пн, ср, чт, сб, вс; длительная — вс
Личные рекорды: 10 км 44:30 (2026-07-04), 21.1 км 1:47:20 (2025-09-15)
Ограничения: правое ахилловое, беспокоит после интервалов
От спортсмена: цель — разменять 1:40; во вторник тренировок не бывает
```

Заодно правим `SYSTEM_PROMPT`: сейчас там зашито «готовящегося к
полумарафону», хотя план может готовить к десятке или марафону. Цель и так
приходит в user-промпте строкой «Цель: …», поэтому в системном промпте
дистанцию не называем.

## Фронтенд

Вкладка `tab-profile`, три карточки:

1. **Профиль спортсмена** — форма по группам полей, под ней строка
   вычисленного (возраст, ИМТ, зоны), кнопки «Сохранить» и
   «Показать контекст для ИИ» (модалка с текстом из `/advise/preview`).
2. **Личные рекорды** — только чтение, из «Стартов».
3. **Настройки ИИ** — как было, только админу; не-админу остаётся
   однострочная подсказка.

Возраст и ИМТ пересчитываются в браузере на лету (арифметика в одну строку),
зоны приходят с сервера при загрузке и после сохранения — формула зон живёт
в одном месте.

Активная вкладка нигде не сохраняется, поэтому переименование — это кнопка
и `id` в `index.html` плюс одна строка в `showTab()`:
`if(name==='profile'){ loadProfile(); if(IS_ADMIN) loadLlmSettings(); }`.
Побочно: `loadLlmSettings()` перестанет дёргаться у не-админов, у которых он
всё равно отвечает 403.

## Приватность

ФИО и дата рождения — персональные данные. Лежат в приватном бакете в
неймспейсе пользователя, доступны только владельцу токена. В `/admin/users`
не попадают — там email и статус; фиксируем тестом.

## Верификация

1. `pytest` зелёный.
2. Dev-стенд: пустой профиль → блока в предпросмотре нет; заполнить → блок
   появился; сохранить дважды → в GCS `athlete/v1/`, `athlete/v2/`, manifest
   указывает на v2, v1 нетронут.
3. Границы: рост 300, ПАНО выше максимального пульса → 400 с понятным текстом.
4. Рекорды подтягиваются из «Стартов», удалённые забеги игнорируются.
5. `/advise` с заполненным профилем — рекомендации учитывают ограничения
   и доступные дни.
