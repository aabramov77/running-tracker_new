# #66 — Оценка недельной нагрузки: две оси (темп + пульс)

- Issue: https://github.com/aabramov77/running-tracker_new/issues/66
- Ветка: `Dev`
- Коммиты: `feat: #66 …` по этапам

## Контекст

Неделя оценивалась только километрами: «Аналитика» показывала объём
план/факт, ИИ-тренер видел км и выполнение плана. Как тяжело прошла неделя,
видно не было: 40 км трусцой и 40 км с интервалами выглядели одинаково.
Нужна недельная нагрузка с учётом интенсивности и её оценка относительно
обычной для спортсмена, чтобы на неё можно было опираться при планировании.

Одна пульсовая метрика этого не даёт: пульс отстаёт на отрезках, врёт при
сбоях датчика и на жаре и не видит рельефа. Поэтому нагрузка считается по
двум осям:

- **внешняя** — что сделано: темп с поправкой на уклон относительно
  порогового (rTSS);
- **внутренняя** — чего это стоило организму: пульс (TRIMP).

Их расхождение («цена работы») — отдельный сигнал усталости, жары или
начинающейся болезни. Нагрузку видят спортсмен и его тренер; тренер — без
профильных параметров, по которым она считается.

Данные на проде (157 пробежек): у всех есть время, темп и средний пульс, у
149 — FIT, где каждые ~5 с записаны пульс, скорость и высота.

## Решения

### Внешняя нагрузка — rTSS

| Вопрос | Решение |
|---|---|
| Формула | Как в TrainingPeaks: `rTSS = часы × IF² × 100`, `IF = NGS / пороговая скорость`, `NGS` — среднее четвёртой степени от скорости с поправкой на уклон, сглаженной за 30 с. 100 = час на пороге |
| Поправка на уклон | Энергозатраты по Минетти: `скорость × C(i) / C(0)`. Уклон по окну ~30 с, ограничен ±30 % |
| Шум GPS | Сглаживание 30 с; скорость выше 7 м/с (2:23/км) отбрасывается |
| Без FIT или без скорости в сэмплах | Оценка по среднему темпу (`pace`, иначе время ÷ дистанция), без уклона. Помечается `≈` |
| Пороговый темп | Поле профиля `threshold_pace_sec`. Не задано — оценка по «Стартам»: по формуле Ригеля (показатель 1,06) прогноз дистанции, которую спортсмен пробежит за час; лучший прогноз среди забегов за 365 дней, иначе — за всё время с пометкой «по забегу от <дата>» |
| Порога нет | Внешняя ось не считается, UI просит указать порог или добавить забег |

### Внутренняя нагрузка — TRIMP

| Вопрос | Решение |
|---|---|
| Формула | **Банистер** по сэмплам: `Σ мин × HRR × a·e^(b·HRR)`, `HRR = (пульс − покой) / (HRmax − покой)`; м: a=0,64, b=1,92, ж: a=0,86, b=1,67 |
| Нет пульса покоя или пола | **Эдвардс**: минуты в зоне × номер зоны (Z1=1 … Z5=5) по действующим зонам. Всё считается на лету, поэтому после заполнения профиля пересчитывается вся история и шкала остаётся единой |
| Без FIT | Средний пульс × длительность. Помечается `≈` |
| Выбросы | Пульс выше HRmax + 10 и ниже 30 не учитывается |
| 80/20 | Минуты недели: лёгкая (ниже Z1 + Z1 + Z2), средняя (Z3), высокая (Z4 + Z5) |

### Оценка недели и цена работы

| Вопрос | Решение |
|---|---|
| Недели | Календарные пн–вс, последние 12, включая текущую. Все неудалённые пробежки, независимо от плана |
| К обычной | По каждой оси: нагрузка недели ÷ среднее за **4 предыдущие** недели. < 0,8 «ниже обычного», 0,8–1,3 «в норме», 1,3–1,5 «выше обычного», > 1,5 «резкий рост». Формулировки нейтральные, без «риска травмы» |
| Мало истории | Оценки нет, если первая пробежка позже, чем за 28 дней до начала недели, если в четырёх предыдущих неделях меньше 4 пробежек с известной нагрузкой или если среднее равно 0 |
| Текущая неделя | Неполная, без оценки. Текущее состояние — скользящие 7 дней ÷ (28 дней до них / 4) |
| Цена работы | TRIMP ÷ rTSS по аэробным пробежкам (лёгкий, длительный, восстановительный). Отклонение от 4 предыдущих недель в пределах ±10 % — «как обычно», выше — «дороже обычного», ниже — «дешевле обычного». Нужны ≥ 2 аэробные пробежки в неделе и ≥ 4 в базе |
| Неизвестная нагрузка | Пробежка без данных не считается; неделя — «не меньше N» со счётчиком неучтённых (принцип #41) |
| «Сегодня» на сервере | Дата UTC, но не раньше даты последней пробежки (максимум +1 день) |

### Хранение

| Вопрос | Решение |
|---|---|
| Кэш | `users/{sub}/derived/run_hist.json`: `{"v": 1, "runs": {"<run_id>": {"hr": {"<уд/мин>": сек}, "spd": {"<см/с>": сек}}}}`. `hr` — время на каждом значении пульса, `spd` — время по корзинам 5 см/с скорости, уже сглаженной и исправленной на уклон |
| Почему гистограммы | Не зависят от профиля: зоны, HRmax, пульс покоя, пол и порог применяются на лету, правка профиля кэш не портит |
| Политика хранения | Кэш — техническое производное от неизменяемого FIT, не бизнес-запись: восстанавливается целиком, поэтому перезаписывается (как `advice/usage.json`). Запись с `if_generation_match`; конфликт не ошибка. Пробежки и детали не меняются, миграции нет |
| Заполнение | При прикреплении FIT (сбой кэша сохранение не ломает) и лениво для старых пробежек: не больше 60 чтений `details.json` за вызов, остаток — `pending`. FIT без пульса или скорости кэшируется пустым. Другой `v` — пересборка |

### Тренер

| Вопрос | Решение |
|---|---|
| Доступ | `GET /coach/athletes/{sub}/load` через `_coached_athlete(c)`, хватает уровня «просмотр» |
| Чего не видит | Пороговый темп, его основание (забег из «Стартов»), источник зон. `coach_load_view` собирает ответ заново по белому списку полей |
| Известное ограничение | По rTSS и темпу пробежки порог можно вычислить обратно — осознанно: темп и пульс пробежек тренер и так видит |
| Запись | Нет: запрос тренера кэш не дозаполняет (`fill_limit=0`) |
| Список спортсменов | Отметка за 7 дней у каждого, подгружается отдельно после показа списка |

## Изменения

### Бэкенд

- **`load.py`** (новый, чистые функции, как `compliance.py`): гистограммы
  пульса и скорости, секунды в зонах, Банистер / Эдвардс, rTSS, оценка
  порога по Ригелю, недели, скользящие 7 дней, цена работы.
- **`storage.py`**: `hr_zone_minutes` через гистограмму (результат прежний);
  кэш `derived/run_hist.json` и его дозаполнение; гистограммы при
  прикреплении FIT; `build_training_load`; `coach_load_view`; поле профиля
  `threshold_pace_sec` и оценка порога в `derived`; блок нагрузки в
  `build_llm_context`.
- **`api.py`**: `GET /load`, `GET /coach/athletes/{sub}/load`; `GET /profile`
  отдаёт оценку порога.
- **`llm_prompt.py`**: блок нагрузки, строка порога в профиле, правила в
  системном промпте: внешняя ось — объём работы, внутренняя — реакция; рост
  цены работы — повод спросить о сне, жаре и самочувствии; оценка «к
  обычной» — с учётом фазы плана.

### Фронтенд

- **Аналитика**: карточка «Недельная нагрузка» — переключатель «по темпу /
  по пульсу», столбцы 12 недель с цветом оценки, пунктир «обычная»,
  подсказка с 80/20, итоги 7 дней, цена работы, «Как считается».
- **Карточка пробежки**: строка «Нагрузка: 62 rTSS · 89 TRIMP», оценки — `≈`.
- **Сегодня**: карточка «Нагрузка за 7 дней»; строка о цене работы — только
  при отклонении больше 10 %.
- **Профиль**: поле «Пороговый темп» с подсказкой об оценке.
- **Тренер**: отметки в списке спортсменов, строка в сводке, та же карточка
  после «Недельного объёма», строка в карточке пробежки.

## Безопасность

- Доступ: `/load` — только `c.sub`; тренер — через `coach_access` по свежему
  реестру, одинаковый 403 для чужого и несуществующего спортсмена.
- Тренеру — белый список полей; скрытые пробежки не попадают ни в суммы,
  ни в счётчики.
- Запрос тренера ничего не пишет; дочитывание деталей — только своих
  пробежек через `read_run_details` (правило #53 о legacy не обходится).
- Ввод порога: неверный тип или вне 2:30–10:00 — 400 `validation_failed`.
- Расчёт терпим к битым данным; в ответе только конечные числа; сбой
  нагрузки не ломает ход ИИ.
- Гистограммы ограничены по построению: пульс 30–230 (≤ 201 ключ), скорость
  с поправкой на уклон — до 14 м/с с шагом 5 см/с (≤ 281 ключ); секунды в
  корзине — не больше двух суток.
- В промпт — только числа и подписи сервера; время забега собирается
  заново из секунд.

## Не входит

- Нагрузка в строках журнала.
- sRPE, нагрузка из часов Garmin, беговая мощность, другие виды активности.
- CTL/ATL/TSB, EWMA, монотонность и strain по Фостеру.
- Плановая нагрузка из текста плана.
- Уведомления тренеру о резком росте нагрузки.

   `/coach/…/load` нет порога.
