# #44 — Интерфейс для тренера

- Issue: https://github.com/aabramov77/running-tracker_new/issues/44
- Ветка: `Dev`
- Коммиты: `feat: #44 …` / `fix: #44 …`

## Контекст

Приложение строго однопользовательское по данным: каждый хендлер в
[api.py](../../api.py) читает только `users/{c.sub}/…`, ролей две
(`admin`/`user`). Issue просит роль «Тренер»: спортсмен выбирает тренера в
Профиле, тренер видит его планы и прогресс, между ними есть диалог.

Это первый случай доступа одного пользователя к данным другого, поэтому
главный риск — не UI, а граница авторизации. План строится вокруг одной точки
проверки доступа и тестов на изоляцию.

Решения, согласованные до реализации:

| Вопрос | Решение |
|---|---|
| Кто тренер | Назначает админ; отметка отдельная от `role` (админ может быть и тренером, и спортсменом) |
| Что видит тренер | Планы, план/факт, графики объёма, журнал пробежек с деталями (круги, пульс, заметки). **Профиль не виден** |
| Диалог | Один общий чат на пару тренер–спортсмен |
| Правка плана тренером | Нет, только просмотр |

Допущения: один тренер у спортсмена; доступ открывается сразу при выборе и
снимается сменой/сбросом; без push — чат обновляется при открытии и опросом.

## Модель данных

**Связь и роль — в реестре** `users/registry.json` (он и так читается на
каждый запрос, и список «мои спортсмены» получается фильтром без обхода
профилей):

- `is_coach: bool` — ставит админ;
- `coach_sub: str | None` — ставит сам спортсмен.

Это авторизационные метаданные, не персональные данные профиля
(`test_registry_never_holds_personal_profile_data` остаётся зелёным). История —
через `append_user_event` (события `coach_grant`, `coach_revoke`,
`coach_select`, `coach_clear`).

**Чат — append-only, сообщение = объект**, в namespace спортсмена:

- `users/{athlete}/coach_chat/{coach}/m/{ts}-{a|c}-{rand}.json` —
  `{id, ts, from_sub, from_role, text}`; объект никогда не перезаписывается,
  гонок read-modify-write нет. Роль автора в имени → непрочитанные считаются
  одним `list_blobs` без скачивания.
- `users/{athlete}/coach_chat/{coach}/read/{reader_sub}.json` — отметка
  «прочитано до ts» (lifecycle-метаданные).

При смене тренера старая ветка остаётся в хранилище, новый тренер её не видит.

## Бэкенд

### `storage.py`

- Пути: `p_chat_msg`, `p_chat_prefix`, `p_chat_read`.
- Реестр: `set_coach_flag(bucket, target_sub, is_coach, actor_sub)` (при снятии
  — очищает `coach_sub` у его спортсменов, с событиями),
  `set_user_coach(bucket, sub, coach_sub|None)` (валидация: цель одобрена,
  `is_coach`, не сам себе), `list_coaches`, `list_athletes_of`.
  Записи делаются по **свежему** реестру, не по кэшу — меньше окно
  потерянного обновления (полное решение — #35).
- `coach_can_access(bucket, coach_sub, athlete_sub)` — единственная проверка
  доступа; читает реестр мимо кэша (TTL 30 с), чтобы отзыв действовал сразу.
  Условие: тренер одобрен и `is_coach`, спортсмен одобрен,
  `athlete.coach_sub == coach_sub`.
- Чат: `append_chat_message`, `read_chat(…, after=None, limit=100)`,
  `chat_unread(…, reader_sub)`, `mark_chat_read`. Текст: не пустой, ≤ 2000.

### `api.py`

`/me` дополнительно отдаёт `is_coach` и `coach`. Таблица `ROUTES` остаётся
4-кортежной; тренерские хендлеры начинаются с общего хелпера
`_athlete_or_403(c)` → `coach_can_access`, одинаковый `403 forbidden` и для
чужого, и для несуществующего sub (нельзя перебирать).

| Метод | Путь | Кто |
|---|---|---|
| POST | `/admin/users/coach` `{sub, is_coach}` | админ |
| GET | `/coaches` | любой одобренный (sub + имя) |
| GET / POST | `/my/coach` `{coach_sub\|null}` | спортсмен |
| GET / POST | `/my/coach/chat` (`?after=`), POST `/my/coach/chat/read` | спортсмен |
| GET | `/coach/athletes` (имя, непрочитанные) | тренер |
| GET | `/coach/athletes/{sub}/plans` | тренер |
| GET | `/coach/athletes/{sub}/plans/{pid}/weeks` | тренер |
| GET | `/coach/athletes/{sub}/plans/{pid}/compliance` | тренер |
| GET | `/coach/athletes/{sub}/runs` | тренер |
| GET | `/coach/athletes/{sub}/runs/{id}/details` | тренер |
| GET / POST | `/coach/athletes/{sub}/chat`, POST `…/chat/read` | тренер |

Чтение — переиспользование существующих функций с sub спортсмена:
`read_plans_index`, `read_plan_weeks`, `build_plan_compliance`, `read_runs`,
`read_run_details`. Проверку владения пробежкой из `h_run_details` вынести в
общий хелпер и вызывать из обоих хендлеров. На данные спортсмена у тренера
только GET — запись даёт 405 автоматически (`match_route`).

## Фронтенд (`app.js`, `index.html`, `style.css`)

- Кнопка навигации «Тренер» видна тренеру и спортсмену с тренером; бейдж
  непрочитанных.
- **Пользователи** (админ): бейдж «тренер» и кнопка «Сделать тренером / Снять»
  в `renderUsers`.
- **Профиль**: карточка «Мой тренер» — выбор из `/coaches`, сохранить,
  отказаться, строка о том, что именно увидит тренер.
- **Новая вкладка `tab-coach`**:
  - спортсмену — чат с тренером;
  - тренеру — список спортсменов → экран спортсмена: сводка, таблица плана
    с план/факт (выбор плана, по умолчанию активный), недельный график,
    журнал (клик → детали с кругами), чат.
- Состояние тренерского экрана — в отдельном объекте `COACH`; глобальные
  `runs`/`PLAN`/`COMPLIANCE` и `localStorage` не трогаются (иначе чужие
  пробежки попали бы в кэш и офлайн-синхронизацию).
- Переиспользование через выделение чистых функций (поведение не меняется):
  - из `renderPlan` (ветка просмотра) → `planViewRowsHtml(plan, weeks, cw)`;
    для спортсмена `cw` берётся из `compliance.current_week`;
  - из `renderLog` → `runItemHtml(run, {readonly})`;
  - из `renderCharts` → `weekChartConfig(planned, exact, actual)`;
  - `showRunDetail` / `loadRunDetailCharts` — параметр источника
    (объект пробежки + URL деталей, без кнопки удаления).
- Чат: опрос раз в 30 с, пока вкладка открыта; `after` — ts последнего
  сообщения.

## Этапы

## Тесты

- `tests/test_registry.py`: назначение/снятие тренера, выбор/сброс, отказы
  (не тренер, сам себе, неизвестный, неодобренный), снятие роли чистит связи,
  события аудита пишутся.
- `tests/test_routes.py`: новые пути разрешаются в свои хендлеры; матрица
  изоляции — не тренер → 403; тренер A не читает спортсмена B; после сброса
  тренера и после снятия роли → 403; несуществующий sub → тот же 403; POST/
  DELETE на данные спортсмена → 405; `/me` отдаёт новые поля; профиль
  спортсмена тренеру недоступен ни одним маршрутом.
- `tests/test_coach_chat.py` (новый): порядок, `after`, лимит, непрочитанные,
  отметка прочтения, существующий объект сообщения не перезаписывается,
  прежний тренер не читает ветку, валидация текста.
- `tests/test_frontend_sanity.py`: `tab-coach` и кнопка есть, статусы и
  колспаны после выделения функций не разъехались.

## Верификация

1. `pytest` — весь набор зелёный.
2. Dev-стенд (`running-tracker-new-4ih.pages.dev`, бэкенд `runs-api-dev`;
   localhost войти не может). Нужны **два одобренных Google-аккаунта** на dev:
   - админ помечает аккаунт A тренером; B выбирает A в Профиле;
   - A видит B в списке, план с план/факт сходится с тем, что видит B;
     журнал и детали пробежки открываются, кнопок правки/удаления нет;
   - B сбрасывает тренера → у A спортсмен пропадает, прямой запрос к
     `/coach/athletes/{B}/runs` даёт 403;
   - сообщения ходят в обе стороны, бейдж непрочитанных появляется и гаснет;
   - собственные данные A (план, журнал, кэш) после просмотра B не изменились.
3. PR `Dev → main` с `Closes #44` — создаётся вручную (интеграция GitHub
   только на чтение).
