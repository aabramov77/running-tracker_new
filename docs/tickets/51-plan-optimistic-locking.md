# #51 — Оптимистическая блокировка записи недель плана

- Issue: https://github.com/aabramov77/running-tracker_new/issues/51
- Ветка: `Dev`
- Коммиты: `fix: #51 …`

## Контекст

Запись недель плана не сверяла версию. `POST /plan` и `POST /plans/{id}/weeks`
передавали в storage только недели, причину и email, а `save_plan_weeks` брал
`current_version + 1` из манифеста, не зная, какую версию видел автор правки.
Клиент шлёт массив недель целиком, поэтому побеждал последний сохранивший:
открытый на десктопе конструктор молча затирал правку, сделанную тем временем
с телефона или кнопкой «Применить» у ИИ-тренера.

CLAUDE.md, «Concurrency requirements»: правку по устаревшей версии отклонять.

Одна такая сверка в коде уже была — у правок ИИ-тренера (#46): предложение
помнит `plan_id` и `plan_version`, `apply_ai_proposal` сравнивает их с
манифестом и отвечает `409 {"error": "proposal_stale"}`. Ручная запись сделана
по тому же образцу.

## Решения

| Вопрос | Решение |
|---|---|
| Как отдать версию, не сломав старый клиент | `GET /plan?meta=1` → `{plan_id, version, weeks}`. Без параметра — прежний голый массив |
| Почему не заголовок | Нужны сразу два значения (план и версия), а кросс-доменный заголовок без `Access-Control-Expose-Headers` молча читается как `null` — блокировка отключилась бы незаметно |
| Что шлёт клиент | `base_version` в теле; для `POST /plan` ещё `base_plan_id` |
| Зачем `base_plan_id` | `POST /plan` пишет в *активный* план, а номера версий у планов свои. Без id «версия 1» старого плана открыла бы запись в новый активный план той же версии |
| Ответ на устаревшую правку | `409 {"error": "plan_stale"}` — зеркало `proposal_stale` |
| Поля нет | Запись без сверки, как раньше: закэшированный старый фронтенд продолжает работать |
| Версия пустого плана | `0`. Первая запись идёт с `base_version: 0`, так что и два устройства с пустым планом друг друга не затрут |

## Изменения

### `storage.py`

- `read_plan_state(bucket, sub, plan_id)` → `{plan_id, version, weeks}`;
  `read_plan_weeks` теперь — его поле `weeks`.
- `PlanStale` — исключение «правка поверх не текущей версии».
- `save_plan_weeks(..., base_version=None)`: при несовпадении с
  `current_version` манифеста поднимает `PlanStale` и ничего не пишет.
  `None` — без сверки.
- `apply_ai_proposal` передаёт в `save_plan_weeks` версию, которую только что
  сверил, и переводит `PlanStale` в `proposal_stale`: ручная правка и правка
  ИИ-тренера проходят через одно и то же предусловие.

### `api.py`

- `_plan_weeks_resp` — общий ответ для `GET /plan` и `GET /plans/{id}/weeks`:
  конверт при `?meta=1`, иначе массив.
- `_save_plan_weeks` — общая запись для обоих `POST`: проверка формата
  `base_version` (целое ≥ 0, иначе `400`), `PlanStale` → `409 plan_stale`.
- `POST /plan`: `base_plan_id`, не равный активному плану, → `409 plan_stale`.

### `app.js`

- `PLAN_BASE = {plan_id, version}` — версия недель, лежащих в `PLAN`.
  `rememberPlan()` кладёт недели и версию в память и в `localStorage` только
  вместе: недели, поднятые из кэша без сети, уйдут на запись со своей версией,
  а не без сверки.
- `loadPlan()` читает `plan?meta=1`; голый массив (бэкенд до #51) → версии нет,
  запись идёт без сверки.
- `postPlanWeeks()` шлёт `base_plan_id` и `base_version`; после успеха берёт
  новую версию из ответа. На `409` перечитывает реестр планов и недели и
  бросает ошибку с `code: 'plan_stale'` и готовым текстом.
- Конструктор: сообщение, остаётся открытым уже со свежими неделями.
  Импорт: сообщение, предпросмотр закрывается (иначе «Отмена» вернула бы
  недели, которых на сервере уже нет).
- `saveDayEdit()` (мобильная правка дня, #48) упрощён: предварительный
  `GET plan` и клиентская сверка ячейки убраны, запись идёт поверх локального
  `PLAN`. На `plan_stale` лист показывает, что теперь стоит в этом дне, и
  предлагает сохранить ещё раз; если сменился активный план или недели больше
  нет — закрывается с сообщением. `fetchPlanWeeks()` больше не нужен и удалён.
- `index.html`: `app.js?v=41`.

## Порядок выкладки

Совместимо в обе стороны, порядок деплоя бэкенда и фронтенда не важен:

- старый фронтенд + новый бэкенд — массив на чтение, запись без сверки;
- новый фронтенд + старый бэкенд — `?meta=1` игнорируется, приходит массив,
  `PLAN_BASE = null`, запись без сверки.

## Что осталось за рамками

- **Атомарность (#35).** Сверка и запись идут двумя операциями: два запроса с
  одной `base_version`, пришедшие одновременно, пройдут оба. Закрыто окно
  «прочитал — минуты правил — записал», а не миллисекундная гонка. Полное
  решение — предусловия записи GCS (`if_generation_match`) во всех версионных
  записях, это #35.

## Тесты

`tests/test_storage.py`:

- `read_plan_state`: версия 0 у пустого плана и без плана, номер после записей;
- запись с верной `base_version` (в том числе первая, с 0) проходит;
- устаревшая и «из будущего» версия → `PlanStale`, хранилище не изменилось;
- вторая «первая» запись с `base_version=0` отклоняется.

`tests/test_routes.py` (оба маршрута — `/plan` и `/plans/{id}/weeks`):

- без `?meta=1` — массив; с ним — `{plan_id, version, weeks}`, версия растёт;
- запись с текущей версией → `201`, версия из ответа годится как следующая основа;
- запись с устаревшей → `409 plan_stale`, ни версии, ни манифеста;
- без поля и с `base_version: null` — как раньше;
- строка, дробное, `true`, отрицательное, список → `400`;
- активным стал другой план → `409`, ни один из планов не тронут.

`tests/test_ai_coach.py`: план переписали между сверкой и записью в
`apply_ai_proposal` → `409 proposal_stale`, чужая правка цела, события
«применено» нет.

`tests/test_frontend_sanity.py` (статически): `loadPlan` читает `plan?meta=1`,
`postPlanWeeks` шлёт `base_version`/`base_plan_id` и на `409` сначала
перечитывает план, потом бросает `plan_stale`; недели и версия пишутся в кэш
только вместе; `saveDayEdit` пишет копию недель через `postPlanWeeks` и
обрабатывает `plan_stale`.
