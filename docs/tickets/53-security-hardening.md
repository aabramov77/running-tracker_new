# #53 — Усиление безопасности перед расширением круга пользователей

- Issue: https://github.com/aabramov77/running-tracker_new/issues/53
- Ветка: `Dev`
- Коммиты: `fix: #53 …`

## Контекст

Приложением пользовался один человек, теперь доступ получат около десяти.
Перед этим проведён аудит; шесть находок относятся к коду и закрыты здесь.
Инфраструктура (IAM, версионирование бакета, число инстансов, лимит расходов
у LLM-провайдера) в тикет не входит — её настраивает владелец.

Общая причина почти всех находок одна: данные пользователя считались своими.
С появлением тренера (#44) это перестало быть верным — данные спортсмена
читает другой человек, в своей сессии.

Уже сохранённые данные не мигрируются. Проверяется то, что пишется сейчас;
чтение остаётся терпимым к старым записям.

## Находки и решения

| № | Что было | Что стало |
|---|---|---|
| 1 | Часть полей пробежки, старта и недели плана попадала в разметку без экранирования | Всё, что пришло с сервера, проходит через `escapeHtml`; id в inline-обработчике — только `Number()` |
| 2 | Запись пробежек, стартов, планов принимала JSON любого типа и размера | Функции `clean_*` в `storage.py`, ответ `400 validation_failed` с полями; предел размера тела |
| 3 | Дневной лимит ИИ-тренера проверялся до вызова модели, а счётчик рос после | Попытка занимается до вызова одной атомарной записью, при сбое модели возвращается |
| 4 | Ленивый перенос legacy-деталей пробежки срабатывал для любого пользователя | Только когда владелец данных — админ по реестру |
| 5 | Ответ `500` содержал текст исключения | Текст уходит в лог, клиенту — `{"error": "internal_error"}` |
| 6 | Роль админа выдавалась по одному совпадению email | Только при `email_verified` в токене |

## Изменения

### 1. Фронтенд — `app.js`, `index.html`

Правило записано комментарием у `escapeHtml`: значение с сервера попадает в
разметку только через `escapeHtml`, а id пробежки или старта в `onclick` —
только через `Number()`. Внутри обработчика экранирование не спасает: браузер
раскодирует атрибут раньше, чем исполнит его как код.

- `runItemHtml`: пульс; id в кнопках разбора и скрытия; дата через
  `String(r.date ?? '')`.
- `openRunDetail`: пульс и самочувствие.
- `planViewRowsHtml`, `planWeekHtml`, строка конструктора: номер недели `w`.
- `renderRaces`: год, id в кнопке; вызовы `showRunDetail(${Number(r.id)})`.
- Заодно обёрнуты значения, которые считает сервер (счётчики, проценты, зоны
  пульса, дата в карточке правок ИИ): сейчас они безопасны, но общая проверка
  исключений не знает.
- `parsePace`, `parseTimeToSeconds`, сортировки по дате не падают, если поле
  пришло не строкой.
- `apiError(res)`: отказ `validation_failed` показывается с перечнем полей, а
  не как «HTTP 400». Старт, отклонённый проверкой, не сохраняется «офлайн».
- `app.js?v=42`.

Идентификаторы-строки в обработчиках остались в трёх местах — id разбора, id
сообщения ИИ и `sub` в списке пользователей. Все три выдаёт сам сервер
(формат проверяется регулярным выражением либо это `sub` из токена Google),
в чужие данные они не попадают.

### 2. Проверка входных данных — `storage.py`, `api.py`, `config.py`

Функции устроены как `clean_athlete_profile`: возвращают значение и словарь
ошибок; хендлер отвечает `400 {"error": "validation_failed", "fields": {…}}`
и ничего не пишет.

| Что | Правила |
|---|---|
| `clean_run` | `id` — целое `1…2^53−1` (может не прийти); `date` — `ГГГГ-ММ-ДД` существующего дня; `dist` — число `0 < x ≤ 1000`; `type` из `TYPE_LABELS`, `feel` из `FEEL_LABELS`; `hr` — пусто или `30…250`; `time`, `pace` — до 32 символов; `notes` — до 2000; `plan_id` — только из своего реестра планов; `fit_token` — формат `write_parsed_fit_to_tmp` |
| `clean_race` | `id`, `date` — как у пробежки; `name` — непустое, до 200; `time` — непустое, до 32; `dist_label` из `DIST_LABEL_KM` |
| `clean_plan_weeks` | список до 104 недель; неделя — объект; `w` — целое `0…999`; `start`, `end`, `type` — до 32; `accent` — до 200; день — до 500 |
| `clean_plan_meta` | `race_name` — до 200; `race_date`, `target_time`, `plan_start` — до 32 |
| `clean_change_reason` | одна строка до 200 символов; не строка — пусто |

Что сделано, чтобы не отвергать законные данные:

- Неделя плана **не дополняется** недостающими полями и **не отвергается** за
  лишние: неизвестные ключи отбрасываются. Фронтенд шлёт назад недели, как
  получил их с сервера (правка одного дня — это весь план целиком), а планы
  до #23 хранятся без вт и чт.
- `null` в текстовом поле — пустая строка, число — его запись текстом
  (в импортированном JSON `target_time` бывает числом).
- `dist` и `hr` принимаются и строкой с числом, как раньше через `float()`.
- Формат дат гонки и недели не проверяется: в неделе это свободный текст
  («10.05»), а в карточке плана значение приходит и из импортированного файла.
- Проверки «Missing field» остались с прежним текстом.

Прочее:

- `Ctx.body()` отдаёт `{}` на любое тело, кроме JSON-объекта; раньше массив в
  теле ронял хендлер.
- `Ctx.query_id()`: нечисловой `?id=` в `DELETE /` и `DELETE /races` — `400`.
- Сбой прикрепления FIT: `400` только на просроченный или неверный токен, без
  текста исключения; остальное — `internal_error`.
- Предел тела: `MAX_JSON_BODY_BYTES` = 1 МБ, `MAX_FIT_BODY_BYTES` = 10 МБ для
  `/runs/parse-fit`. Объявленная длина сверяется до проверки токена — `413`.
  Для тела без объявленной длины (chunked) тот же предел передаётся
  фреймворку через `request.max_content_length`, а его отказ при чтении
  (исключение с кодом 413) становится тем же ответом.

### 3. Дневной лимит ИИ — `storage.py`, `api.py`, `tests/conftest.py`

- `reserve_advice_usage(bucket, sub, limit)` читает счётчик вместе с номером
  поколения объекта (`bucket.get_blob`) и пишет его с `if_generation_match`.
  `PreconditionFailed` или `NotFound` (прочитанное поколение уже перезаписано)
  — читаем заново, до восьми раз. `None` — лимит исчерпан.
- `release_advice_usage` тем же способом возвращает попытку.
- `UsageBusy` — счётчик не удалось записать ни с одной попытки. Модель тогда
  не вызывается: `429 {"error": "usage_busy"}`.
- `h_ai_message_post`: резерв после всех бесплатных проверок и до
  `build_ai_turn`; возврат — при сбое модели, неразборчивом ответе и любом
  исключении до ответа.
- `increment_advice_usage` удалена: неатомарного пути больше нет.

`tests/conftest.py` — основа, которую просит #35: у `FakeBucket` каждый объект
имеет номер поколения, растущий при любой записи; `upload_from_string`
понимает `if_generation_match` (`0` — «объекта ещё нет»); есть `get_blob` и
`reload`; объект с известным поколением читает именно его и получает
`NotFound`, если оно перезаписано; заглушки
`google.api_core.exceptions.PreconditionFailed` и `NotFound`. Версионные
записи (`write_*_version`) из #35 не тронуты.

### 4. Legacy-детали — `storage.py`

`read_run_details` переносит детали из корня бакета, только если `sub`
(владелец данных) — админ по реестру (`_is_admin`). Тренер админа приходит с
`sub` админа и детали видит. Проверка стоит внутри функции, поэтому действует
и там, где детали читаются для контекста ИИ.

### 5. Тексты ошибок — `api.py`

`handle_request`: `logging.exception(...)` с методом и путём, клиенту —
`{"error": "internal_error"}`. Фронтенд текст пятисотых не разбирает; у
ИИ-тренера код заменяется человеческой фразой.

### 6. Админ по email — `storage.py`

`resolve_user`: админ — это адрес из `ADMIN_EMAILS` и `email_verified`
(`true` или строка `"true"`) в токене. Без подтверждения — обычная заявка,
которая идёт в счёт `MAX_PENDING`.

## Тесты

`tests/test_security.py` — по разделу на находку 2–6, всего 157 тестов.
На коде до исправления падают 142; остальные 15 фиксируют, что законные
данные по-прежнему проходят.

- Находка 2: по параметру на каждое плохое значение каждого поля пробежки,
  старта, недели и карточки плана — `400`, виновато ровно это поле, в
  хранилище ничего не появилось. Отдельно: форма фронтенда сохраняется как
  отправлена; разрежённые и старые недели; лишние ключи; нечисловой `?id=`;
  тело не-объект; `413` для JSON и для FIT, в том числе без токена.
- Находка 3: пять запросов при лимите 1 — пока модель «отвечает» первому,
  приходят остальные четыре: один `201`, четыре `429`, модель вызвана один
  раз. Гонка двух записей счётчика в четырёх вариантах (счётчика ещё нет или
  он есть; соперник вклинился до или после чтения). Возврат попытки при сбое
  модели и при сбое до неё. Счётчик, который не удаётся записать. Смена суток.
  Поведение самого фейкового бакета.
- Находка 4: пользователь с пробежкой, чей id совпал с legacy, получает `404`,
  в его namespace ничего не скопировано; админ и тренер админа детали видят.
- Находка 5: исключение с путём и ключом в тексте — в ответе их нет, в логе есть.
- Находка 6: неподтверждённый адрес админа — обычная заявка без админских
  маршрутов и без обхода лимита регистраций.

`tests/test_frontend_sanity.py` — пять тестов:

- `test_server_values_are_escaped_before_markup` разбирает все шаблонные
  литералы `app.js` и в тех, что содержат разметку, не допускает подстановки,
  выводящей поле данных как есть. На прежнем `app.js` находит 16 мест.
- Тест на сам разборщик, чтобы он не пропускал всё подряд.
- Поимённые проверки там, куда общая не дотягивается: id в обработчиках,
  строки карточки пробежки, дата не строкой.

Поправлены существующие тесты: админский токен теперь с `email_verified`;
счётчик расходуется через `reserve_advice_usage`; legacy-fallback проверяется
на админе; два теста реестра читают объект заново, а не через `Blob`,
запомнивший своё поколение.

## Верификация

- `python -m pytest` — 828 passed, 1 skipped (было 666).
- Находка 1 проверена в браузере на локально поднятой странице с подменённым
  `fetch`: в `hr`, `feel`, `w`, `id`, а также в дате, типе, темпе, названии и
  дистанции старта стояла разметка с обработчиками. Отрисованы журнал,
  таблица плана, конструктор, неделя списком, «Сегодня», старты, карточка
  пробежки и экран тренера; нажаты строки и кнопки списков. Обработчики не исполнились ни
  разу, посторонних элементов в разметке нет, текст виден как текст; в
  `onclick` вместо строки стоит `NaN`. Тот же стенд на разметке, вставленной
  как есть, исполнение фиксирует.

### Что проверить на dev-стенде после выкладки

Локально нет ни Flask, ни настоящего GCS, поэтому два места проверены только
на заглушках:

1. Обычные запросы проходят (сохранить пробежку, план, старт, загрузить FIT):
   это подтверждает, что `request.max_content_length` и `if_generation_match`
   у настоящих библиотек ведут себя как ожидается.
2. Сообщение ИИ-тренеру проходит, счётчик «сегодня N из M» растёт на единицу.

## Вне тикета

Замечено по ходу, не исправлялось:

- `_ask_llm` отдаёт пользователю текст ошибки провайдера (`Provider 4xx: …`).
- `h_profile_post`, `h_llm_config_post`, `h_my_coach_post` на значение
  неожиданного типа отвечают `500` (теперь без текста исключения), а не `400`.
- Число планов на пользователя и размер `runs.json` ничем не ограничены.
- `POST /` с существующим `id` заменяет запись в `runs.json` на месте.
