# #25 — Работа с несколькими планами

- **Issue:** [#25 Работа с несколькими планами](https://github.com/aabramov77/running-tracker_new/issues/25)
- **Статус:** план (реализация не начата)

## Контекст

Сейчас у пользователя ровно **один** план тренировок и **один** профиль гонки:

- `users/{sub}/plan/manifest.json` + `plan/v{N}/plan.json` — единственный план
- `users/{sub}/profile.json` — `{race_name, race_date, target_time, plan_start}`,
  одна гонка на пользователя
- `users/{sub}/runs.json` — плоский список, привязки к плану нет

Нужно: несколько планов под разные соревнования, выбор плана на вкладке «План»,
привязка пробежки к плану.

## Согласованные решения

| Вопрос | Решение |
|---|---|
| Журнал и аналитика | Переключатель **«все / текущий план»**, по умолчанию — активный план |
| Привязка пробежки | Автоматически к активному плану, в форме можно сменить |
| Существующие пробежки | Все привязать к мигрированному плану |

**Ключевое упрощение:** «выбранный» и «активный» план — одно и то же понятие.
Селектор на вкладке «План» переключает активный план (сохраняется на сервере),
и от него зависят заголовок, обратный отсчёт, метрики, дефолт в форме пробежки
и контекст для LLM.

**Данные гонки переезжают в план.** План = подготовка к конкретному старту,
поэтому `race_name/race_date/target_time/plan_start` становятся полями плана,
а не глобального профиля.

## Архитектура данных (после)

```
users/{sub}/
  plans/
    index.json                  ← мутабельный реестр планов + active_plan_id
    {plan_id}/
      manifest.json             ← указатель на текущую версию недель
      v{N}/plan.json            ← иммутабельные версии {version, weeks: [...]}
  runs.json                     ← у каждой пробежки появляется plan_id
  profile.json                  ← legacy: не читается после миграции, не удаляется
  plan/                         ← legacy одиночный план: остаётся для истории
```

`plans/index.json`:
```json
{
  "active_plan_id": "1755100000000",
  "plans": [
    {
      "id": "1755100000000",
      "race_name": "Полумарафон",
      "race_date": "2026-08-09",
      "target_time": "1:40",
      "plan_start": "2026-05-10",
      "created_at": "ISO",
      "archived": false
    }
  ]
}
```

**CLAUDE.md-compliance:** `index.json` — мутабельный реестр (прецедент:
`users/registry.json`, `plan/manifest.json`, `profile.json` уже перезаписываются).
Содержимое недель остаётся **иммутабельно версионируемым** внутри каждого плана.
Удаление плана — логическое (`archived: true`), объекты не удаляются.

## Шаг 1. Backend (`main.py`)

### 1.1. Пути

```python
def p_plans_index(sub):            return f"{upfx(sub)}plans/index.json"
def p_plan_manifest(sub, pid):     return f"{upfx(sub)}plans/{pid}/manifest.json"
def p_plan_ver(sub, pid, v):       return f"{upfx(sub)}plans/{pid}/v{v}/plan.json"
# legacy одиночный план (только для миграции)
def p_singleplan_manifest(sub):    return f"{upfx(sub)}plan/manifest.json"
```

Существующие `p_plan_manifest(sub)` / `p_plan_ver(sub, v)` получают параметр
`plan_id` — все вызовы обновляются.

### 1.2. Реестр планов

```python
def read_plans_index(bucket, sub)                 # {} → авто-миграция (см. 1.4)
def write_plans_index(bucket, sub, index)
def create_plan(bucket, sub, meta)                # новый id, запись в index, становится активным
def set_active_plan(bucket, sub, plan_id)
def update_plan_meta(bucket, sub, plan_id, meta)  # race_name/date/target/plan_start
def archive_plan(bucket, sub, plan_id)            # archived=true; если был активным — переключить
def get_active_plan(bucket, sub)                  # запись плана или None
```

### 1.3. Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/plans` | `{active_plan_id, plans: [...]}` (запускает ленивую миграцию) |
| POST | `/plans` | создать план `{race_name, race_date, target_time, plan_start}` → станет активным |
| POST | `/plans/active` | `{plan_id}` — переключить активный |
| POST | `/plans/{id}/meta` | изменить данные гонки плана |
| POST | `/plans/{id}/archive` | логическое удаление |
| GET | `/plans/{id}/weeks` | недели конкретного плана |
| POST | `/plans/{id}/weeks` | сохранить новую версию недель |

`GET/POST /plan` **сохраняем** как шорткат на недели **активного** плана —
меньше правок на фронте и совместимость при раскатке.

### 1.4. Ленивая миграция (автоматическая, на первом `GET /plans`)

Если `plans/index.json` отсутствует:

1. Прочитать `profile.json` (данные гонки) и `plan/manifest.json` (текущие недели).
2. Создать план с новым `id`, метаданными из профиля (при пустом профиле —
   пустые поля), записать текущие недели как **v1** нового плана.
   Старые версии остаются по legacy-пути `users/{sub}/plan/v*` для истории —
   не копируем и не удаляем.
3. Записать `index.json` с этим планом как активным.
4. Проставить `plan_id` **всем** пробежкам в `runs.json` (решение №3).
5. Идемпотентность: повторный вызов ничего не делает (index уже есть).

Пользователь без плана и профиля → пустой `index.json`, миграция ничего не пишет.

### 1.5. Пробежки

- `POST /` (runs): принимает `plan_id`; если не передан — подставляется активный.
- `GET /` возвращает пробежки как есть (фильтрация — на фронте, чтобы работал
  переключатель «все / план» без лишних запросов).

### 1.6. LLM-контекст

`build_llm_context(bucket, sub)`: брать активный план и **только его пробежки**
(`plan_id == active`), даты недели считать от `plan_start` активного плана.
В `write_advice_version` добавить `plan_id` в payload.

## Шаг 2. Frontend (`app.js`, `index.html`)

### 2.1. Вкладка «План»
- Над таблицей — строка: селектор планов (`<select>`), кнопки **«+ Новый план»**
  и **«✏ Гонка»** (редактирование `race_name/date/target/plan_start` текущего плана).
- Смена в селекторе → `POST /plans/active` → перезагрузка недель, заголовка, метрик.
- Пустое состояние (планов нет) → «Создать план» (форма гонки + пустой конструктор).
- Архивирование плана — в форме «Гонка» кнопка «Архивировать».

### 2.2. Данные гонки
`PROFILE` заменяется на `ACTIVE_PLAN` (метаданные активного плана).
`applyProfileToHeader()`, `planStartDate()`, `planWeeks()`, `renderMetrics()`,
`renderCharts()` берут данные оттуда. Карта «Моя гонка» из «Настроек»
переезжает во вкладку «План» (гонка теперь свойство плана).

### 2.3. Форма пробежки
- Новое поле **«План»** — `<select>` со списком неархивированных планов,
  предвыбран активный; значение уходит в `plan_id` при `POST /`.
- FIT-загрузка: `plan_id` добавляется так же, как `fit_token`.

### 2.4. Журнал и аналитика
- Переключатель **«Текущий план / Все»** (сегмент-кнопки) в журнале и аналитике.
- Состояние в JS (`logScope = 'plan' | 'all'`), по умолчанию `plan`.
- `renderLog`, `renderMetrics`, `renderCharts`, `renderAdjust` фильтруют
  `runs` по `plan_id === ACTIVE_PLAN.id`, когда scope = `plan`.
- В журнале при scope = `all` показывать бейдж с названием плана.

### 2.5. Кэш
Ключи localStorage дополняются активным планом там, где кэшируются недели:
`running_tracker_plan__{sub}__{plan_id}`.

Cache-buster `app.js?v=19`.

## Верификация

1. **Миграция:** у админа (13+ недель, ~N пробежек) первый `GET /plans` создаёт
   один план с данными из `profile.json`; все пробежки получают его `plan_id`;
   план и журнал выглядят как раньше. Повторный вызов — без изменений.
2. **Новый план:** создать второй план (другая гонка, свой `plan_start`) →
   появляется в селекторе, становится активным, недели пустые (конструктор).
3. **Изоляция:** пробежка, сохранённая при активном плане B, не видна
   в журнале при активном плане A (scope = «Текущий план»); при scope = «Все»
   видна с бейджем плана.
4. **Заголовок и метрики:** переключение плана меняет название гонки,
   обратный отсчёт, «неделя X из N» и недельный график.
5. **LLM:** «Запросить рекомендации» при активном плане B использует только
   его пробежки и его план недель.
6. **Архив:** архивированный план исчезает из селектора и из выпадающего списка
   в форме пробежки; его данные не удаляются в GCS.
7. **Тесты:** `pytest` зелёный, включая новые тесты реестра и миграции.
