# Spec Delta

## Purpose

Кто и как получает доступ к API и данным: вход по Google ID-токену, заявка и одобрение, роли, изоляция данных каждого пользователя и общая защита API от некорректных и чрезмерных запросов.

## ADDED Requirements

### Requirement: Запрос несёт Google ID-токен
Каждый запрос к API, кроме предварительного `OPTIONS`, SHALL нести заголовок `Authorization: Bearer <Google ID token>`, выданный для клиента приложения и с действительной подписью. Без заголовка, с чужим или недействительным токеном ответ MUST быть `401 {"error": "Unauthorized"}`.

#### Scenario: Запрос без токена
- **WHEN** клиент вызывает `GET /plans` без заголовка `Authorization`
- **THEN** ответ `401 {"error": "Unauthorized"}`

### Requirement: CORS и предварительный запрос
API SHALL отвечать на `OPTIONS` кодом `204` с заголовками CORS: разрешён любой источник, методы `GET, POST, DELETE, OPTIONS`, заголовки `Content-Type, Authorization`, `Access-Control-Max-Age: 3600`. Эти же заголовки MUST быть у каждого JSON-ответа.

#### Scenario: Предварительный запрос браузера
- **WHEN** браузер шлёт `OPTIONS /plans`
- **THEN** ответ `204` без тела с `Access-Control-Max-Age: 3600`

### Requirement: Регистрация при первом входе
Первый запрос с токеном неизвестного пользователя SHALL создавать запись в реестре: идентификатор Google (`sub`), почта, имя, статус `pending`, роль `user`, и событие аудита `register`. Повторный и параллельный первый вход того же пользователя MUST давать одну запись.

#### Scenario: Новый пользователь ждёт одобрения
- **WHEN** пользователь впервые входит с действительным токеном
- **THEN** в реестре появляется его запись со статусом `pending`
- **AND** записано событие `register`

### Requirement: Администратор по подтверждённой почте
Пользователь, чья почта входит в список администраторов и подтверждена Google (`email_verified`), SHALL при первом входе получать статус `approved` и роль `admin`. Неподтверждённая почта из списка MUST давать обычную заявку `pending` без админских прав и без обхода лимита заявок.

#### Scenario: Неподтверждённая почта админа
- **WHEN** входит пользователь с почтой из списка администраторов, но `email_verified: false`
- **THEN** его статус `pending`, роль `user`
- **AND** админские маршруты отвечают ему `403`

### Requirement: Лимит заявок
Если в реестре уже 50 заявок в статусе `pending`, регистрация нового пользователя (не администратора) SHALL отклоняться ответом `403 {"error": "registration_closed"}` без записи в реестр.

#### Scenario: Очередь заявок заполнена
- **WHEN** при 50 ожидающих заявках входит новый пользователь
- **THEN** ответ `403 {"error": "registration_closed"}`

### Requirement: Статус доступа доступен любому вошедшему
`GET /me` SHALL отвечать при любом статусе пользователя: `status`, `role`, `email`, `name`, `is_coach` и выбранный тренер (`coach`).

#### Scenario: Заявка на рассмотрении
- **WHEN** пользователь со статусом `pending` вызывает `GET /me`
- **THEN** ответ `200` с `status: "pending"`

### Requirement: Без одобрения API закрыт
Пользователю не в статусе `approved` любой маршрут, кроме `/me`, SHALL отвечать `403` с `error` `pending_approval` (заявка ждёт) или `rejected` (отклонён) и полем `status`. Проверка MUST идти до разбора пути, чтобы по кодам ответа нельзя было перебирать маршруты.

#### Scenario: Отклонённый пользователь
- **WHEN** пользователь со статусом `rejected` вызывает `GET /plans`
- **THEN** ответ `403 {"error": "rejected", "status": "rejected"}`

#### Scenario: Несуществующий путь у неодобренного
- **WHEN** пользователь со статусом `pending` вызывает несуществующий путь
- **THEN** ответ `403 pending_approval`, а не `404`

### Requirement: Экраны статуса в интерфейсе
После входа интерфейс SHALL показывать заставку, пока сервер подтверждает доступ, затем приложение (`approved`), экран «на рассмотрении» (`pending`) или экран отказа (иной статус). Ответ `401` MUST сбрасывать сохранённый токен и возвращать стартовую страницу.

#### Scenario: Истёкший токен
- **WHEN** запрос приложения получает `401`
- **THEN** токен удаляется из браузера и показывается стартовая страница

### Requirement: Админские маршруты
Маршруты администрирования (`/admin/*`, `/config/llm*`) SHALL отвечать пользователю без роли `admin` кодом `403 {"error": "forbidden"}`.

#### Scenario: Обычный пользователь открывает список пользователей
- **WHEN** пользователь с ролью `user` вызывает `GET /admin/users`
- **THEN** ответ `403 {"error": "forbidden"}`

### Requirement: Изоляция данных пользователя
Свои данные (планы, пробежки, старты, профиль, разборы и память ИИ-тренера, нагрузка) SHALL читаться и писаться только для пользователя из токена; параметров, выбирающих чужие данные, у этих маршрутов MUST NOT быть. Роль администратора MUST NOT давать доступа к чужим данным. Единственное исключение — тренер (capability `coach-access`).

#### Scenario: Чужая история не находится
- **WHEN** пользователь запрашивает историю пробежки с id чужой пробежки
- **THEN** ответ `404`, данные другого пользователя не раскрываются

### Requirement: Кэш браузера разделён по пользователям
Данные, которые интерфейс кэширует в браузере, SHALL храниться под ключами конкретного пользователя; выход MUST очищать состояние прежнего пользователя (разборы ИИ, нагрузку, незаконченные правки, списки скрытых).

#### Scenario: Смена пользователя в одном браузере
- **WHEN** один пользователь выходит, а другой входит в том же браузере
- **THEN** второй не видит кэшированных пробежек и разборов первого

### Requirement: Неизвестный путь и метод
Неизвестный путь SHALL отвечать `404 {"error": "Not found"}`. Известный путь с неподдерживаемым методом MUST отвечать `405 {"error": "Method not allowed"}` с заголовком `Allow`, перечисляющим допустимые методы.

#### Scenario: DELETE на маршрут плана
- **WHEN** одобренный пользователь шлёт `DELETE /plans`
- **THEN** ответ `405` с `Allow: GET, OPTIONS, POST`

### Requirement: Предел размера тела запроса
Тело запроса SHALL быть не больше 1 МиБ, а для загрузки FIT (`POST /runs/parse-fit`) — не больше 10 МиБ. Больше — ответ `413 {"error": "payload_too_large", "limit_bytes": N}` до проверки токена и без записи данных; тело без объявленной длины MUST обрываться на том же пределе.

#### Scenario: Слишком большой JSON
- **WHEN** клиент шлёт пробежку с телом 2 МиБ
- **THEN** ответ `413` с `limit_bytes: 1048576`, ничего не записано

### Requirement: Проверка входных данных
Тело записи SHALL проверяться по полям до записи: неверный тип, выход за пределы длины или диапазона дают `400 {"error": "validation_failed", "fields": {поле: что не так}}`, и ничего MUST NOT записываться. Тело, не являющееся JSON-объектом, MUST считаться пустым.

#### Scenario: Тело — массив вместо объекта
- **WHEN** клиент шлёт `POST /` с телом `[1, 2]`
- **THEN** ответ `400`, пробежка не создаётся

### Requirement: Внутренние ошибки не раскрываются
Необработанная ошибка SHALL давать `500 {"error": "internal_error"}`; текст исключения, пути объектов и ответы внешних сервисов MUST NOT попадать клиенту и уходят в журнал сервера.

#### Scenario: Сбой хранилища внутри обработчика
- **WHEN** обработчик падает с исключением, в тексте которого путь объекта
- **THEN** клиент получает только `internal_error`
