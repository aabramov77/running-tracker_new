# Design

## Context

Мотивация — в proposal.md (Why). Поведение приложения задокументировано в
README, тикетных планах `docs/tickets/N-*.md` и тематических `docs/*.md`,
а точнее всего — в коде (`api.py` с таблицей маршрутов `ROUTES`,
`storage.py`, `compliance.py`, `load.py`, `history.py`, `weather.py`,
`llm_prompt.py`, `app.js`) и в ~1270 тестах `tests/`. Спеки собираются из
этих источников и описывают состояние кода на `52c56ff`.

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемое поведение: HTTP-контракт, ошибки, правила
  доступа и приватности, видимое в интерфейсе.
- Дать будущим change опорные требования для `MODIFIED`-дельт.

**Non-Goals:**
- Исправлять код или документацию: найденные расхождения — только в Open
  Questions.
- Описывать реализацию: имена функций и модулей, библиотеки, раскладку
  объектов в GCS.
- Описывать целевое («как должно быть») поведение.

## Decisions

### База через change, а не прямую запись в `openspec/specs/`
Спеки пишутся как дельты `ADDED` и попадают в `openspec/specs/` через
`openspec archive`. Альтернатива — писать основные спеки сразу — быстрее,
но не оставляет в `changes/archive/` следа: когда и из каких источников
собрана база. Через change процесс тот же, что у всех будущих фич.

### Три волны с ревью
Ядро (данные, доступ, планы, пробежки, старты) → профиль, аналитика, ИИ →
тренер и интерфейс. Порядок — по зависимостям: поздние capability ссылаются
на ранние (например, `ai-plan-proposals` и `coach-plan-editing` опираются на
версии плана из `training-plans` и `versioned-storage`).

### Соглашения по тексту спеки
- Текст на русском; заголовки OpenSpec и `SHALL`/`MUST` — на английском
  (`openspec/config.yaml`).
- Одно поведение на `### Requirement:`, описание ≤ 500 символов, у каждого —
  хотя бы один `#### Scenario:` с `WHEN`/`THEN`.
- В спеку входят маршруты, коды и тела ошибок, видимое поведение UI,
  ограничения доступа. Не входят: имена функций, модулей, библиотек и пути
  объектов в бакете. Инвариант хранения («каждая версия — новый
  неизменяемый объект, прежний не перезаписывается») — входит.
- Источник истины — код и тесты. Расхождение с README → в спеку поведение
  кода, расхождение — в Open Questions.
- Сценарии по возможности повторяют проверки из `tests/test_*.py`.
- Общее поведение описывается один раз: версии, логическое удаление и
  `base_version` — в `versioned-storage`; остальные capability ссылаются на
  него и описывают только свои коды ошибок и поля.

## Risks / Trade-offs

- [Спека описывает поведение неточно] → каждое требование сверяется с
  хендлером и тестами; ревью пользователя после каждой волны.
- [Спека быстро устаревает] → после архива любое изменение поведения
  проходит через change с `MODIFIED`-дельтой.
- [Слишком детальные спеки мешают рефакторингу] → в спеку не входят
  внутренние имена и раскладка хранилища.

## Open Questions

Расхождения документации и кода, найденные при сборке спек. Спеки
описывают поведение кода; решение о правке — отдельным change.

### Волна 1

1. **Карточка и архив плана — без версий.** Реестр планов — изменяемый
   объект: правка карточки гонки меняет его на месте и пишет событие
   «было → стало», а архивирование ставит `archived` и `archived_at` без
   события аудита. Политика хранения (CLAUDE.md) требует запись аудита на
   каждое удаление. Спеки (`training-plans`) описывают поведение кода.
2. **Офлайн-запись не синхронизируется.** Без связи новая пробежка и
   скрытие сохраняются только в браузере, а сообщение обещает
   синхронизацию «при подключении». Механизма синхронизации нет: следующая
   загрузка журнала с сервера заменяет локальный список, и офлайн-записи
   теряются. В `run-log` описано только сохранение в браузере.
3. **Карточка пробежки.** README: «графики пульса и темпа по дистанции,
   таблица кругов». В коде графики пульса и темпа по времени, высоты и
   темпа по кругам; таблицы кругов нет. `activity-import` — по коду.
4. **Подписи типов недели.** README: «развивающая / пиковая / подводка /
   загрузочная / гонка». Интерфейс и формат импорта: «Развитие / Пик /
   Тейпер / Разгрузка / Старт»; у `load` смысл расходится («загрузочная» и
   «Разгрузка»). Спеки — по интерфейсу.
5. **«Отмена» в конструкторе плана** закрывает режим правки, но добавленные
   и удалённые недели остаются на экране до перезагрузки (на сервер они не
   уходят). В `training-plans` зафиксировано только «без записи».
6. **Порядок журнала.** README называет журнал хронологией; список идёт в
   порядке добавления пробежек (по `id`), а не по дате тренировки.
7. **Путь объекта в ответе.** `POST /plans/{id}/weeks` и `POST /plan`
   возвращают, кроме номера версии, внутренний `gcs_object_path`. В спеке
   контракт ответа — номер версии.

### Волна 2

8. **Anthropic как провайдер.** README в разделе ИИ-тренера называет OpenAI
   и DeepSeek, а в таблице стека — ещё и Anthropic. API принимает
   `anthropic`, интерфейс его не предлагает; для него не передаются глубина
   рассуждения и JSON-режим, а бюджет вывода — 1500 токенов вместо 8000.
   `llm-config` фиксирует оба факта.
9. **Порядок истории профиля.** `GET /profile/history` отдаёт версии от
   старых к новым, а истории плана, пробежек, стартов и памяти — от новых к
   старым.
10. **Сутки лимита ИИ-тренера** считаются по UTC, а не по часовому поясу
    пользователя: у спортсмена в Москве счётчик сбрасывается в 03:00.
11. **«Пропущено» у будущих дней.** API план/факта ставит статус
    `missed` и дням, которые ещё не наступили; интерфейс прячет отметки
    будущих недель, а мобильный вид отличает будущий пропуск сам. Клиенту
    API без интерфейса это легко прочитать как пропуск.
