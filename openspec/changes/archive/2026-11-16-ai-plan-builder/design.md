# Design

## Context

Мотивация — в proposal.md. Требования — в `specs/ai-plan-builder/spec.md` и дельтах. Что уже есть в коде и что определяет подход:

- **Разборы ИИ-тренера (`storage.py`, `api.py`).**
  - У карточки разбора уже есть поле `kind`: `run` или `general` (`create_ai_thread`).
  - Ход идёт так (`h_ai_message_post`):
    1. Попытка занимается атомарно (`reserve_advice_usage`).
    2. Собирается контекст (`build_ai_turn`).
    3. Вызывается модель (`_ask_llm`), ответ разбирается (`parse_coach_reply`).
    4. Только после успеха пишутся вопрос и ответ (`append_ai_message`); при сбое попытка возвращается (`release_advice_usage`).
  - Реплики — отдельные неизменяемые объекты `ai_coach/t/{tid}/m/{msg}.json`.
- **Предложения правок.** Сервер сверяет предложение с окном недель (`clean_proposal`) и хранит его в реплике. Состояние считается на чтении (`mark_proposal_states`). Применение пишет версию плана поверх `base_version` (`apply_ai_proposal`). Черновик нового плана устроен по той же схеме.
- **Вызов модели.**
  - Бюджет вывода `LLM_MAX_TOKENS = 8000` (`config.py`) покрывает и рассуждение.
  - HTTP-таймаут 60 с на вызов (`_post_chat`).
  - Cloud Run разворачивается без `--timeout`, значит действует таймаут запроса по умолчанию — 300 с.
- **Планы.**
  - `create_plan(meta, make_active, author)` правит реестр `plans/index.json` условной записью через `update_json` с повтором: при гонке `change` вызывается заново на свежем реестре.
  - `save_plan_weeks(..., base_version, author)` пишет версию через `commit_version`. `base_version=0` значит «недель ещё не было».
  - `clean_plan_weeks` проверяет состав недель.
- **Даты.**
  - `compliance.week_windows` понимает строки с подписями `ДД.ММ`, в том числе укороченную первую.
  - Год берётся из `plan_start`.
  - `parse_planned_day` даёт нижнюю границу объёма ячейки.
- **Оценка формы.** `load.estimate_threshold` выбирает лучший забег за год (часовой темп по Ригелю, `RIEGEL_EXP = 1.06`). Этот же выбор годится для прогноза на целевую дистанцию.
- **Предпросмотр импорта (`app.js`).**
  - `applyImportedPlan` временно подменяет `PLAN`, включает режим правки и показывает бар с действиями.
  - `saveImportedAsNewPlan` создаёт план через `POST /plans` и `POST /plans/{id}/weeks`.
  - Конструктор и импорт доступны только на десктопе (`desktop-only`).

## Goals / Non-Goals

**Goals:**
- Переиспользовать ход разбора целиком. Новый вид разбора отличается только сборкой системной части и разбором конверта ответа, без отдельного маршрута диалога.
- Детерминированное — на сервере: даты, число недель, тип и акцент недель, день старта, проверки. Модель пишет только содержание.
- Сбой модели не оставляет следов: ни реплик, ни частичного черновика, ни списанной попытки.

**Non-Goals:**
- Не меняем формат недель плана и набор типов недель.
- Не делаем просмотр и правку неактивного плана без активации. Неактивный план из черновика правится после активации обычным конструктором.
- Не делаем стриминг ответа и фоновые задачи: генерация укладывается в один HTTP-запрос.

## Decisions

### 1. Новый вид разбора `plan`, а не отдельный мастер
`create_ai_thread` принимает `kind` (`plan` или по умолчанию). `build_ai_turn` ветвится по `thread["kind"]`:
- **инструкция:** `plan_builder_instructions()` вместо `coach_chat_instructions()`;
- **окно правок:** не строится (`with_proposals=False`);
- **дополнительные блоки данных:**
  - «Бриф и календарь» последнего принятого брифа разбора;
  - «Оценка цели»;
  - «Последний каркас», сжатая таблица недель, чтобы правка каркаса опиралась на него, а не на пересказ в истории.

`h_ai_message_post` после `parse_coach_reply` для разбора `plan` вызывает `clean_brief` / `clean_outline` вместо `clean_proposal`. Принятое кладётся в ответ полями `brief` / `outline`. Отклонённое даёт `draft_rejected: ["brief"|"outline"]`.

*Альтернатива:* отдельный мастер с формой и одним вызовом модели. Отклонено: в issue прямо просят диалог, а диалог уже даёт память, контекст, лимит и интерфейс.

### 2. Бриф и календарь
`clean_brief(raw, today)` проверяет поля по спеке и нормализует их:
- даты — ISO;
- дистанция — число км;
- цель — `parse_time_to_sec` → строка; пусто значит «финишировать»;
- дни — коды `mon`…`sun`.

Если даты начала нет, подставляется ближайший понедельник после сегодня.

`brief_calendar(brief)` строит недели:
- первая — от даты начала до воскресенья;
- дальше — пн–вс;
- у плана к старту — до недели с датой старта, у общего — `weeks` штук.

Результат — `[{"w", "start_date", "end_date", "start": "ДД.ММ", "end": "ДД.ММ"}]`. Больше `AI_PLAN_WEEKS_MAX = 30` — бриф отклоняется.

Последний принятый бриф ищется в репликах разбора: последняя реплика `ai` с `brief`. Бриф хранится в реплике целиком, календарь пересчитывается из него на лету. Это детерминированная функция брифа, хранить её нечего.

*Почему 30 недель:* генерация кусками по 4 недели — это 8 параллельных вызовов, и каркас на 30 недель ещё помещается в ответ хода. Марафонская подготовка обычно 16–24 недели. При старте дальше инструкция просит начать позже.

### 3. Оценка цели
`goal_assessment(brief, races, today)` вычисляет:
- `weeks`;
- `min_weeks` по дистанции: ≤5 км → 4, ≤10 → 6, ≤21,1 → 8, длиннее → 12;
- `prediction` — время по Ригелю от того же забега, который выбирает `estimate_threshold`: лучший часовой темп за год, без забегов за год — нет прогноза;
- `gap` — разницу с целью.

В промпт уходит строкой. Тот же расчёт даёт предупреждение «мало недель» к каркасу.

### 4. Каркас
`clean_outline(raw, calendar)` требует ровно `len(calendar)` недель с номерами 1..N:
- тип — из `PLAN_PHASE_LABELS`;
- `km` — число 0–300;
- `accent` и `key` — одна строка до 200 символов;
- `paces` — до 8 пар `{name, value}` по 60 символов.

`outline_warnings(outline, brief, usual_km, assessment)` вычисляет:
- рост больше 15 % к прошлой неделе, кроме недели после `load`;
- первую неделю больше `1.3 × usual_km`;
- мало недель.

`usual_km` — обычный объём из профиля, а если его нет — средний по нагрузке за 4 недели.

### 5. Генерация недель кусками, параллельно
`POST …/messages/{msg}/weeks` (`h_ai_plan_weeks`):
1. Находит реплику с `outline`. Её бриф берётся по `outline.brief_message_id`: это id реплики, чей бриф каркас проверял (свой, если бриф пришёл в том же ответе). Id записывается вместе с каркасом, поэтому позднейшие брифы на каркас не влияют.
2. Занимает попытку как ход диалога.
3. Режет календарь на куски по `AI_PLAN_CHUNK_WEEKS = 4` недели и вызывает модель по каждому куску параллельно (`ThreadPoolExecutor`, до 8 потоков).
4. Каждый вызов получает компактную системную часть: инструкцию генерации, профиль, рекорды, пульсовые зоны, ограничения брифа, весь каркас и таблицу дней куска с датами, доступностью и пометкой дня старта. Пробежки и история не передаются: каркас их уже учёл, а вход меньше — значит быстрее.
5. Ответ куска: `{"weeks": [{"week": k, "mon": "...", …}]}`.
6. `clean_chunk` принимает только недели своего куска. Ячейки — одна строка до 200 символов. Дни вне окна недели обнуляются.
7. Кусок без всех своих недель повторяется один раз; повтор тоже неполный — `502 llm_bad_draft`.
8. Сборка: `w`, `start`, `end` — из календаря; `type`, `accent` — из каркаса; ячейку дня старта сервер ставит сам.
9. Недели проходят `clean_plan_weeks`, затем считаются предупреждения черновика.
10. Пишутся реплика спортсмена «Расписать план по неделям» и реплика `ai` с `plan_draft` и текстом, составленным сервером. Запрос записывается в историю, чтобы чередование вопрос → ответ для провайдера не ломалось.

Любой сбой — `release_advice_usage`, и ничего не пишется. Токены всех вызовов суммируются в ответе.

*Альтернатива:* один вызов на весь план. Отклонено: около 140 ячеек на русском — 4–6 тыс. токенов вывода плюс рассуждение. Это близко к бюджету 8000 и к таймауту 60 с.

*Альтернатива:* куски по очереди, каждый со своим HTTP-запросом от фронтенда. Отклонено: попытка и атомарность черновика размазываются по нескольким запросам, а частичный черновик пришлось бы хранить.

*Почему параллельно:* куски независимы при зафиксированном каркасе. Последовательно 8 кусков по 30–40 с упираются в 300 с Cloud Run. Параллельно время равно самому медленному куску плюс повтор.

### 6. Создание плана: идемпотентность через реестр
`create_plan_from_draft(bucket, sub, thread_id, msg_id, make_active, weeks=None, created_by)`:
1. Читает реплику, проверяет `plan_draft` (`no_plan_draft`). Если пришли `weeks`, прогоняет их через `clean_plan_weeks` (`validation_failed`).
2. Вызывает `_update_plans_index` с `change`:
   - есть план с `ai_source.message_id == msg_id` → `AlreadyCreated(plan_id)`;
   - иначе добавляет карточку из брифа с `created_by_role: "ai"`, `created_by_sub: sub`, `ai_source: {thread_id, message_id}` и ставит активным, если `make_active` или активного нет.

   Проверка и добавление происходят в одной условной записи, поэтому из двух одновременных запросов план добавит один, а второй на повторе увидит его и получит `already_created`.
3. Пишет `save_plan_weeks(..., draft_weeks, "ИИ-тренер: новый план", base_version=0, author=plan_author("ai", sub))`.
4. Если `weeks` отличаются от черновика, пишет `save_plan_weeks(..., weeks, "Правка черновика ИИ-тренера", base_version=1, author=plan_author("athlete", sub))`.

Создание `create_plan` не переиспользуется как есть, потому что проверка дубля должна жить внутри того же `change`. Общая сборка карточки выносится в хелпер.

*Сбой между шагами 2 и 3* (план есть, недель нет): повтор получит `already_created`. Чтобы не оставлять пустой план, при `already_created` сервер проверяет манифест: если недель нет, дописывает версию 1 (и 2, если пришли правки) и отвечает `201`. `base_version=0` защищает от двойной записи.

*Альтернатива:* отдельный маркер `ai_coach/t/{tid}/created/{msg}.json`, как у `applied`. Отклонено: маркер и план пишутся двумя записями, а повторить «маркер есть, плана нет» без перезаписи маркера нельзя. Реестр же — единственный источник правды о существовании плана.

### 7. Состояние черновика на чтении
`mark_draft_states` один раз читает реестр и ставит `plan_draft_state` (`created` + `plan_id` / `open`) репликам с `plan_draft`. Это делается в `h_ai_thread_get` рядом с `mark_proposal_states`.

### 8. Инструкции модели
В `llm_prompt.py`:
- **`PLAN_BUILDER_SYSTEM_PROMPT`.** Роль и стиль общие с `COACH_CHAT_SYSTEM_PROMPT`: общая часть выносится в константу, разделы «Просьба составить план» и «Как писать» остаются у обычного разбора. Дальше:
  - шаги: бриф → подтверждение → каркас → кнопка;
  - принципы периодизации;
  - что брать из данных, а что спрашивать;
  - реалистичность цели;
  - формат `brief`/`outline` с примером;
  - напоминание, что план создаёт спортсмен.
- **`PLAN_WEEKS_PROMPT`** — для генерации куска: стиль ячеек, понятный разбору план/факт («10 км легко», «14–16 км длительный», интервалы — «8 км: 5×1 км по 4:30»); не трогать день старта и дни вне окна; только JSON.
- **В обычном разборе** раздел «Просьба составить план» меняется: кратко описать подход и предложить «🤖 Составить с ИИ».

Блоки данных: `format_brief_block`, `format_goal_assessment`, `format_outline_block`, `format_chunk_days`.

### 9. Фронтенд
- **Вход.** `aiPlanBuilder()`: `showTab('aicoach')`, `aiNewThread()`, затем `aiSend({text: 'Хочу составить новый план', kind: 'plan'})`. В `aiSend` при создании разбора передаётся `kind`. Подсказка в `AI_STARTERS` делает то же. Кнопка «🤖 Составить с ИИ» стоит в `index.html` рядом с «+ Новый план».
- **Список разборов.** Пометка «🗓» у `kind === 'plan'`.
- **Карточки в `aiMessageHtml`.**
  - `aiBriefHtml` — кнопка подтверждения только у последнего брифа без каркаса после него;
  - `aiOutlineHtml` — недели полосой цветом типа и столбики км на CSS, без Chart.js;
  - `aiDraftHtml` — сводка, раскрываемая таблица, действия;
  - пометка `draft_rejected`.
- **`aiGenerateWeeks(msgId)`** — подтверждение; пока идёт запрос, статус «Тренер расписывает недели…».
- **`aiCreatePlan(msgId)`.** Если активного плана нет — `confirm` и создание. Иначе на карточке раскрывается выбор из двух кнопок: «Сделать активным» / «Активировать позже» и «Отмена». После успеха — `loadPlans()`; если план стал активным, ещё `loadPlan()`, и карточка перерисовывается в `created`.
- **«Сделать активным»** у созданного черновика вызывает существующий `switchPlan(planId)`.
- **Предпросмотр черновика.** Через обобщение `applyImportedPlan`: бар получает режим `draft` со своими текстами и кнопками, а `_importedRace` заменяется карточкой из брифа, чтобы даты и предупреждения считались от `plan_start` черновика. «Создать…» шлёт `create-plan` с `weeks` из `collectPlanEdits()`. Кнопка видна только на десктопе, как импорт.
- **Переключатель планов.** Пометка `' · от ИИ'` у `created_by_role === 'ai'`.

## Risks / Trade-offs

- **[Качество плана зависит от модели]** → Каркас подтверждает человек. Проверки и предупреждения ловят грубые ошибки: объём, дни, день старта. Черновик можно поправить до создания, а после создания он правится обычным конструктором.
- **[Каркас на 30 недель в ответе хода может оборваться по бюджету]** → Инструкция требует короткие `accent`/`key` (до ~80 символов). Обрыв даёт `llm_truncated`, попытка возвращается, спортсмен повторяет. Если будет повторяться, поднять бюджет для хода разбора `plan`. Это решение реализации, спеку оно не меняет.
- **[Параллельные вызовы упираются в лимиты провайдера]** → До 8 одновременных запросов от одного пользователя. Ошибка 429 провайдера — это `llm_provider_error`, и попытка возвращается. При частых сбоях уменьшить параллельность (константа).
- **[Таймаут Cloud Run]** → Самый медленный кусок плюс повтор — около 120 с, это меньше 300 с по умолчанию. При реализации проверить фактический `timeoutSeconds` сервиса (`gcloud run services describe`), а не полагаться на умолчание.
- **[Стоимость: генерация — одна попытка, но до 8 вызовов]** → Так решил пользователь. Число вызовов и токены пишутся в ответ для аудита. Отдельный лимит — вне объёма.
- **[Неактивный план из черновика нельзя посмотреть без активации]** → Правки до создания есть в предпросмотре конструктора. После создания карточка черновика предлагает «Сделать активным».
- **[Черновик устаревает: дата начала прошла]** → План всё равно создаётся с прошлой первой неделей, а карточка показывает дату начала. Специальной блокировки нет, это решение спортсмена.

## Migration Plan

Миграции данных нет. Новые поля реестра (`created_by_role: "ai"`, `ai_source`) и реплик (`brief`, `outline`, `plan_draft`, `draft_rejected`) необязательные. Старый код их игнорирует, старые реплики и планы читаются как раньше. Откат — откат кода: разборы `plan` остаются в хранилище, а прежний фронтенд покажет их как обычные разборы.
