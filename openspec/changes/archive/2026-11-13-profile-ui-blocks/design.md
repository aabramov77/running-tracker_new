# Design

## Context

Мотивация — в `proposal.md`. Здесь только то, что определяет подход.

- Фронтенд — статические `index.html` / `app.js` / `style.css` без сборщика.
  Поля профиля размечены в `index.html` статически (`id="pr-*"`), `app.js`
  заполняет их из ответа `GET /profile` и собирает обратно при сохранении.
- `POST /profile` заменяет профиль целиком и пишет новую версию. Поле,
  которого нет в теле, сбрасывается (кроме пяти «поздних» полей, которые
  сервер берёт из текущей версии). Принимает необязательный `change_reason`.
- Проверки значений живут только на сервере; ответ `400 validation_failed`
  несёт словарь «поле → текст ошибки».
- `GET /profile` уже отдаёт всё вычисляемое: возраст, ИМТ, оценку и
  действующий максимальный пульс, расчётные и действующие зоны с источником,
  действующий порог с источником и основанием.
- Вкладка перечитывает профиль при каждом открытии и перезаполняет форму.
  Так же при каждом открытии перечитываются тренер (`GET /coaches`,
  `GET /my/coach?fresh=1`) и, у администратора, конфиг модели
  (`GET /config/llm`); загрузка конфига очищает поле ключа.
- «Мой тренер» — список тренеров и «Сохранить» (`POST /my/coach`, с
  подтверждением смены и снятия), а переключатель права на правку планов
  сохраняется сразу отдельным маршрутом `POST /my/coach/plan-edit`.
- «Настройки LLM» — форма провайдера, модели, глубины и ключа
  (`POST /config/llm`). Ключ сервер требует при каждой записи
  (`400 Missing api_key`) и никогда не отдаёт, только маску. «Проверить
  ключ» (`POST /config/llm/test`) проверяет уже сохранённый конфиг.
- Статические тесты `tests/test_frontend_sanity.py` завязаны на разметку
  редактора зон, на функции сбора и заполнения формы и на то, что сохранение
  профиля перезагружает нагрузку и погоду.
- Замеры текущего экрана и макет — в `docs/tickets/87-profile-ui.md`.

## Goals / Non-Goals

**Goals:**
- Изменить одно значение — открыть один блок и сохранить его, не листая форму.
- Одна модель взаимодействия на всей вкладке: просмотр → «Изменить» →
  «Сохранить» / «Отмена» — для профиля, тренера и настроек модели.
- Сводка заполненного профиля на телефоне не длиннее двух экранов (сейчас 4,1).
- Обойтись без изменений API, сервера и формата данных.
- Сохранить `id` полей и существующие статические проверки профиля.

**Non-Goals:**
- Сверка версии при записи профиля (`base_version`). Её нет и сейчас; это
  серверное изменение со своей дельтой спеки.
- Показ истории профиля (`GET /profile/history`) во фронте.
- Сохранение настроек модели без повторного ввода ключа: нужна правка
  `POST /config/llm` на сервере.
- Изменение маршрутов `/my/coach`, `/my/coach/plan-edit`, `/config/llm` и
  подтверждений смены тренера.
- Проверка значений на клиенте: правила остаются в одном месте, на сервере.
  Исключение — уже существующая проверка непустого ключа модели перед
  запросом; она остаётся как есть.

## Decisions

### 1. Сводка и правка по блокам, а не аккордеон или мастер

Согласовано с пользователем 2026-11-11. Аккордеон с общей кнопкой дешевле,
но оставляет одну форму и одно сохранение на всё. Пошаговый мастер удобен
для первого заполнения и мешает основному сценарию — точечной правке.

### 2. Границы блоков — по связанным проверкам сервера

| Блок | Поля |
|---|---|
| `personal` «Личное» | `full_name`, `birth_date`, `sex`, `height_cm`, `weight_kg` |
| `hr` «Пульс и зоны» | `hr_max`, `hr_threshold`, `hr_rest`, `hr_zones_custom` |
| `pace` «Порог и МПК» | `threshold_pace_sec`, `vo2max` |
| `training` «Режим тренировок» | `years_running`, `weekly_km_typical`, `sessions_per_week`, `available_days`, `long_run_day` |
| `weather` «Погода и место» | `location`, `run_time`, `cold_sensitivity`, `venues` |
| `health` «Здоровье и пожелания» | `injuries`, `notes` |

Сервер сверяет ПАНО, пульс покоя и начало Z5 с максимальным пульсом, а день
длительной — с доступными днями. Обе группы целиком внутри одного блока,
поэтому ошибка сохранения блока всегда относится к полю этого же блока.
Альтернатива — прежние шесть секций («Физиология» вместе с порогом, зоны
отдельно) — разносила бы максимальный пульс и зоны по разным блокам.

### 3. Блок раскрывается на месте, без листа и модального окна

Поведение одно на десктопе и на телефоне. Редактору зон и поиску города
нужен полный размер, а нижний лист (как у правки дня) ограничен 85 % высоты
и прячет остальной профиль. Открытый блок прокручивается в видимую область.

### 4. Сохранение шлёт весь профиль; значения закрытых блоков — из формы

Поля закрытых блоков остаются в разметке скрытыми и всегда равны последнему
ответу сервера: форма перезаполняется после загрузки, после сохранения и
при отмене. Поэтому сбор формы не меняется, а в запрос добавляется только
`change_reason`.

Альтернативы:
- Частичная запись на сервере (слать только поля блока). Меняет контракт
  `POST /profile`: сейчас отсутствующее поле означает сброс, и на это
  опирается правило о «поздних» полях. Затронуло бы сервер, спеку и других
  клиентов API ради того, что решается на клиенте.
- Собирать тело как «сохранённый профиль + поля блока». Значения в ответе
  сервера и в полях формы имеют разный вид (секунды и «м:сс», число и
  строка), понадобился бы второй путь преобразования рядом с существующим.

### 5. Поля остаются статической разметкой, сводку рисует скрипт

Поля переезжают в блоки без смены `id`. Сводка каждого блока строится из
последнего ответа сервера. Всё, что вводил спортсмен (ФИО, травмы, заметки,
название места), попадает в разметку только экранированным — это уже
проверяет общий сканер шаблонов в тестах.

Альтернатива — рисовать и поля скриптом — ломает статические проверки строк
редактора зон и inline-обработчиков без пользы для пользователя.

### 6. Ошибки раскладываются по полям на клиенте

Словарь «поле → ошибка» из ответа сервера сопоставляется с элементами формы.
Для составных полей якорь — их контейнер: доступные дни, редактор зон,
строка поиска города, площадки. Ошибка поля, которого нет в открытом блоке
(по решению 2 не ожидается), выводится строкой у кнопок блока с подписью
поля — как сейчас.

### 7. Защита несохранённого: подтверждение и отказ от перезаполнения

«Изменён ли блок» определяется сравнением текущих значений полей блока со
снимком, снятым при открытии. Подтверждение — системный диалог, как у
черновика плана тренера. При возврате на вкладку изменённый открытый блок
не перезаполняется — ни загрузкой профиля, ни загрузкой тренера, ни
загрузкой конфига модели; неизменённый — перечитывается как обычно.

Альтернатива — спрашивать при уходе с вкладки — потребовала бы вмешаться в
общее переключение вкладок, которым пользуются все разделы.

### 8. Причина версии — «Профиль: <название блока строчными>»

Например, «Профиль: пульс и зоны». История версий показывает, что меняли,
без сравнения полей. Сервер уже обрезает и нормализует причину.

### 9. Подсказки — из ответа `GET /profile`, по списку с приоритетом

Условия перечислены в спеке. Порядок: нет зон → нет порога → нет города →
максимальный пульс по оценке → нет пульса покоя или пола. Показываются
первые две. Новых запросов и новых полей в ответе не требуется.

### 10. Кнопка «Показать контекст для ИИ» сохраняет название

Она описана в спеке `ai-coach-dialog`; переезжает в шапку профиля без
переименования, чтобы не менять ещё одну capability.

### 11. Один механизм блока, три вида сохранения

Открытие, отмена, «изменён ли блок», подтверждение и правило «открыт один
блок» — общие для всех блоков вкладки. У каждого блока свои поля, своя
сводка и своя запись: шесть блоков профиля — `POST /profile`, «Мой
тренер» — `POST /my/coach` с прежними подтверждениями, настройки модели —
`POST /config/llm`. Блоки `coach` и `llm` добавляются в тот же список
блоков, что и блоки профиля.

Альтернатива — оставить карточкам их нынешнее устройство — сохраняет на
одной вкладке два способа правки, а от этого #87 и уходит.

### 12. Переключатель права на правку планов — мгновенный и в просмотре

У переключателя свой маршрут, и это правка в одно касание. Под
«Изменить» одно «Сохранить» слало бы два запроса (`/my/coach` и
`/my/coach/plan-edit`) с риском, что пройдёт только первый. К тому же при
выборе нового тренера сервер сам возвращает право к значению по умолчанию.

### 13. «Проверить ключ» — в просмотре

Кнопка проверяет сохранённый конфиг. В открытой форме, рядом с полем
ключа, её естественно принять за проверку введённого ключа — сейчас так и
есть. Без сохранённого конфига кнопка недоступна: сервер всё равно ответил
бы `LLM config not set`.

### 14. Ключ модели вводится при каждом сохранении

Сервер требует ключ и не отдаёт его, поэтому сохранить «без смены ключа»
нельзя, не меняя `POST /config/llm`. Форма прямо говорит, что ключ нужен
при каждом сохранении. Существующая проверка пустого ключа выводит ошибку
под полем ключа. Поле ключа очищается при «Отмене» и после сохранения;
в кэш и `localStorage` ключ не попадает.

## Risks / Trade-offs

- [Вкладка с устаревшим профилем затирает правку с другого устройства:
  уходит весь профиль, сверки версии нет] → риск тот же, что у нынешней
  формы; профиль перечитывается при каждом открытии вкладки. Полное
  решение — `base_version` на сервере, отдельным изменением.
- [Форма закрытых блоков разошлась с последним ответом сервера, и
  сохранение одного блока меняет чужие поля] → перезаполнение формы в трёх
  точках (загрузка, сохранение, отмена); проверка в браузере: тело запроса
  при сохранении одного блока отличается от сохранённого профиля только
  полями этого блока.
- [Статические тесты ищут конкретные строки в функциях профиля] → имена
  функций сбора, заполнения и сохранения не меняются; тесты прогоняются
  после каждой группы задач.
- [Сводка из шести карточек длиннее ожидаемого на телефоне] → цель — два
  экрана; строки сводки объединяют близкие значения («182 см · 74,5 кг»).
- [Системный диалог подтверждения выглядит чужеродно] → принят ради
  единообразия с остальным приложением.
- [Смена или снятие тренера отнимает у него доступ к данным] → прежние
  подтверждения из `coach-access` остаются; «Сохранить» недоступна, пока
  выбор не изменён.
- [Введённый ключ модели лежит в поле, пока блок открыт] → блок виден
  только администратору; поле очищается при отмене и сохранении и никуда,
  кроме запроса `POST /config/llm`, не уходит.
- [Обязательный ключ при каждом сохранении неудобен администратору] →
  ограничение сервера, в форме есть пояснение; снять его можно отдельным
  серверным изменением.

## Migration Plan

Изменение только во фронтенде. Данные не мигрируют; версии профиля,
выбор тренера и конфиг модели пишутся теми же запросами, что и сейчас. Выкладка — обычным путём `Dev → main`; версии `app.js?v=`
и `style.css?v=` поднимаются. Откат — возврат коммита.

## Open Questions

- Точные формулировки строк «на что влияет блок», текстов подсказок и
  пояснения о ключе модели уточняются при реализации: спеки фиксируют
  условия, а не тексты.
