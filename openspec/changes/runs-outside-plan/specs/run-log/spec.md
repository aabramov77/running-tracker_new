# Spec Delta

## MODIFIED Requirements

### Requirement: Привязка пробежки к плану
`plan_id` SHALL приниматься только из планов самого пользователя; чужой или несуществующий план даёт `400 validation_failed`. `plan_id: null` или `""` MUST означать «без плана», в том числе при правке. Если ключа `plan_id` нет, новая пробежка MUST привязываться к плану по своей дате, а при правке сохранять прежнюю привязку.

#### Scenario: Пробежка без плана в запросе
- **WHEN** спортсмен с активным планом сохраняет новую пробежку без ключа `plan_id`, и дата пробежки попадает в окна недель активного плана
- **THEN** пробежка привязана к активному плану

#### Scenario: Правка сохраняет план
- **WHEN** спортсмен правит пробежку из прошлого плана без ключа `plan_id`
- **THEN** привязка к прошлому плану сохраняется

#### Scenario: Явно без плана
- **WHEN** спортсмен с активным планом сохраняет новую пробежку с `plan_id: null`
- **THEN** пробежка сохранена без плана (`plan_id: null`)

#### Scenario: Отвязка правкой
- **WHEN** спортсмен правит пробежку, привязанную к плану, и присылает `plan_id: null`
- **THEN** создаётся новая версия пробежки с `plan_id: null`
- **AND** прежняя версия с привязкой к плану остаётся в истории правок

### Requirement: Журнал пробежек
`GET /` SHALL отдавать текущие нескрытые пробежки в порядке добавления, последние первыми (правка места не меняет). Журнал MUST показывать дату, неделю («Нед N» — только у пробежек активного плана), тип, дистанцию, самочувствие, темп с цветом (быстрее 4:48 — хороший, до 5:18 — средний, медленнее — отстающий), время, пульс, заметки; фильтр «текущий план» / «без плана» / «все», к «все» — название плана.

#### Scenario: Фильтр по плану
- **WHEN** спортсмен выбирает «текущий план», а в нём пробежек нет
- **THEN** журнал предлагает переключиться на «Все» или добавить пробежку

#### Scenario: Фильтр «без плана»
- **WHEN** спортсмен выбирает «Без плана»
- **THEN** журнал показывает только нескрытые пробежки с `plan_id: null`
- **AND** при отсутствии таких пробежек сообщает, что пробежек вне планов нет

#### Scenario: Пробежка вне активного плана в журнале
- **WHEN** в области «все» показана пробежка без плана или из другого плана
- **THEN** у неё нет метки «Нед N» активного плана

## ADDED Requirements

### Requirement: Привязка по дате
Новая пробежка без ключа `plan_id` SHALL привязываться к неархивному датированному плану, в окна недель которого (от начала первой до конца последней) попадает её дата. При нескольких подходящих MUST выбираться активный, иначе — начавшийся позже. Если подходящего плана нет, пробежка MUST сохраняться без плана. Недатированный план в выборе не участвует.

#### Scenario: Пробежка между планами
- **WHEN** у спортсмена план A закончился 31 августа, план B начинается 1 октября, и он сохраняет без ключа `plan_id` пробежку от 15 сентября
- **THEN** пробежка сохранена без плана

#### Scenario: Пробежка после окончания активного плана
- **WHEN** активный план закончился, и спортсмен сохраняет без ключа `plan_id` пробежку с сегодняшней датой
- **THEN** пробежка сохранена без плана, а не в активный план

#### Scenario: Дата в неактивном плане
- **WHEN** дата новой пробежки попадает только в окна неактивного неархивного плана
- **THEN** пробежка привязана к этому плану

#### Scenario: Дата в двух планах
- **WHEN** дата новой пробежки попадает и в активный, и в другой план
- **THEN** пробежка привязана к активному плану

#### Scenario: Нет планов
- **WHEN** у спортсмена нет ни одного плана
- **THEN** новая пробежка сохраняется без плана

#### Scenario: Недатированный план
- **WHEN** у единственного плана нет ни подписей недель, ни даты старта
- **THEN** новая пробежка без ключа `plan_id` сохраняется без плана

### Requirement: Выбор плана в форме пробежки
Форма записи SHALL показывать список «План» всегда, даже без планов, с пунктами «Авто (по дате)», «Без плана» и неархивными планами. Новая пробежка MUST по умолчанию получать «Авто», и запрос уходит без ключа `plan_id`. «Без плана» MUST отправлять `plan_id: null`. При правке MUST быть выбран план пробежки или «Без плана».

#### Scenario: Новая пробежка по умолчанию
- **WHEN** спортсмен открывает форму новой пробежки и сохраняет её, не трогая список «План»
- **THEN** запрос не содержит ключа `plan_id`, и сервер привязывает пробежку по дате

#### Scenario: Выбор «Без плана»
- **WHEN** спортсмен выбирает «Без плана» и сохраняет пробежку
- **THEN** запрос содержит `plan_id: null`

#### Scenario: Правка пробежки без плана
- **WHEN** спортсмен открывает на правку пробежку с `plan_id: null`
- **THEN** в списке «План» выбран пункт «Без плана»
