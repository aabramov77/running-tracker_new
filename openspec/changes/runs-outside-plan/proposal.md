# Proposal

Issue: [#71 Корректно отражать тренировки в период между планами](https://github.com/aabramov77/running-tracker_new/issues/71)

## Why

Если у спортсмена есть хотя бы один план, новая пробежка без `plan_id` привязывается к **активному** плану, какая бы у неё ни была дата. Пробежка до старта плана, после его окончания или в промежутке между планами попадает в чужой план и искажает его план/факт. Явно сохранить пробежку «без плана» нельзя: в форме такого пункта нет, а пустой `plan_id` сервер понимает как «по умолчанию». Поэтому отвязать пробежку правкой тоже невозможно, и отдельно посмотреть пробежки вне планов тоже нельзя.

## What Changes

- **Привязка по дате вместо «к активному».** Если `plan_id` не пришёл, новая пробежка привязывается к плану, в окна недель которого попадает её дата. Учитываются только датированные неархивные планы. Если подходят несколько планов, выигрывает активный, иначе тот, что начался позже. Если не подходит ни один (между планами, до первого, после последнего), пробежка сохраняется без плана. **BREAKING** (поведение API): раньше такая пробежка всегда уходила в активный план.
- **Явное «без плана» в API.** Ключ `plan_id` со значением `null` (или `""`) значит «без плана». Отсутствие ключа по-прежнему значит «по умолчанию»: для новой пробежки это привязка по дате, при правке прежняя привязка сохраняется. Если правкой отвязать пробежку от плана, создаётся новая версия, история не теряется.
- **Форма пробежки.** В списке «План» появляются пункты «Авто (по дате)» (по умолчанию для новой пробежки) и «Без плана», затем планы. При правке выбрана текущая привязка пробежки или «Без плана». Список виден всегда, даже если планов нет.
- **Область «Без плана».** В журнал и аналитику добавляется третья кнопка «Без плана» рядом с «Текущий план» и «Все». Она показывает пробежки с `plan_id = null`. График в этой области строится так же, как в области «все»: без плановых столбцов.
- **Метка «Нед N».** Метка в журнале показывается только у пробежек активного плана. Пробежка без плана или из другого плана не получает номер недели активного плана.

Вне объёма:
- аналитика по календарным неделям без плана (замена захардкоженного старта `2026-05-10` и «из 13» в метриках);
- массовая перепривязка уже сохранённых пробежек; отдельные пробежки можно перепривязать правкой;
- область «Без плана» в карточке спортсмена у тренера;
- Android-клиент.

## Capabilities

### New Capabilities

### Modified Capabilities
- `run-log`: меняется требование «Привязка пробежки к плану» (привязка по дате, явное «без плана», отвязка правкой) и «Журнал пробежек» (область «Без плана», метка «Нед N» только для пробежек активного плана, пункты «Авто»/«Без плана» в форме).
- `training-load`: требование «Сводка и графики аналитики» — область «Без плана» без плановых столбцов.

## Impact

- **Бэкенд:** `storage.py` (`clean_run` различает отсутствие `plan_id` и явный `null`; `save_run` получает решение о привязке); `api.py` (`h_run_post` вместо активного плана выбирает план по дате); `compliance.py` (используются `week_windows`/`anchor_source` для диапазона дат плана).
- **Фронтенд:** `index.html` (кнопки области, список `f-plan`); `app.js` (`renderPlanSelectors`, `saveRun`, `fillRunForm`, `scopedRuns`, `setRunScope`, `renderLog`, `renderCharts`).
- **Тесты:** `tests/test_storage.py`, `tests/test_routes.py` (привязка по дате, явный `null`, отвязка правкой); `tests/test_frontend_sanity.py` при необходимости.
- **Данные:** миграции нет. Уже сохранённые пробежки сохраняют свою привязку. Формат версии пробежки прежний (`plan_id: null` уже допустим).
- **Офлайн-очередь:** пробежка с «Авто» уходит без ключа `plan_id`, и сервер привяжет её по дате при синхронизации.
