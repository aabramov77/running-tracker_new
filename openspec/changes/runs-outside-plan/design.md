# Design

## Context

Сейчас поведение такое (мотивация — в proposal.md):

- `clean_run` (`storage.py`) превращает и отсутствующий `plan_id`, и `null`/`""` в `None`. `save_run` подставляет `None` → прежний план (правка) или `default_plan_id`. `h_runs_post` (`api.py`) передаёт туда активный план. Различить «по умолчанию» и «без плана» на сервере нельзя.
- Окна недель плана уже умеет считать `compliance.week_windows(weeks, plan_start)`. Признак датированности даёт `compliance.anchor_source(...)` (`DEFAULT`/`UNDATED` — план не датирован). `storage.py` уже импортирует `compliance`.
- Фронтенд: список `f-plan` заполняется только планами и скрыт, если планов нет. `saveRun` кладёт `plan_id` только при непустом значении. Область журнала и аналитики — `runScope` (`'plan' | 'all'`), фильтр — `scopedRuns()`. Кнопки `.scope-btn[data-scope]` есть в двух местах `index.html` (журнал и аналитика) и синхронизируются в `setRunScope`.
- Офлайн-запись копит новую пробежку локально и отправляет её позже обычным `POST /`.

## Goals / Non-Goals

**Goals:**
- Сервер сам решает привязку по дате, и клиенту не нужно знать недели неактивных планов.
- Контракт API обратно совместим по форме: те же поля, `plan_id: null` уже был допустимым значением в версии пробежки.

**Non-Goals:**
- Не трогаем расчёт план/факт (`plan-compliance`): факт по-прежнему считается по пробежкам, привязанным к плану.
- Не пересчитываем привязку существующих пробежек и не меняем её при правке даты пробежки: при правке без ключа `plan_id` привязка сохраняется, как раньше.

## Decisions

### 1. «Без плана» = ключ присутствует со значением `null`/`""`; «по умолчанию» = ключа нет
`clean_run` возвращает признак `plan_explicit` (ключ `plan_id` есть в теле). Тогда `null`/`""` дают `plan_id: None` при `plan_explicit=True`. `save_run` применяет умолчание (прежний план при правке или план по дате для новой пробежки) только при `plan_explicit=False`.

*Альтернатива:* отдельное строковое значение-маркер (`"none"`). Отклонено: это смешивает идентификатор плана со служебным значением, а `null` в JSON и так означает «нет плана». Риск, что старый клиент шлёт `plan_id: ""`, имея в виду «по умолчанию», проверен: текущий фронтенд при пустом выборе ключ не кладёт (`if (planSel && planSel.value)`). Android-клиент `plan_id` не шлёт.

### 2. Привязка по дате считается на сервере при создании
Новая функция `plan_for_date(bucket, sub, index, day)` в `storage.py`:
1. Берёт неархивные планы из реестра.
2. Для каждого читает недели (`read_plan_weeks`) и пропускает недатированные (`anchor_source(...) == UNDATED`) и пустые.
3. Считает диапазон `[первое окно.start, последнее окно.end]` через `week_windows(weeks, plan.plan_start)`.
4. Из подходящих планов выбирает активный; иначе план с самым поздним началом диапазона.

`h_runs_post` передаёт в `save_run` не `default_plan_id`, а вычисленный план. Чтобы не читать недели при правке, `save_run` принимает либо готовое значение, либо функцию `default_plan(day)`, которую вызывает только для новой пробежки (`prev is None`) без явного `plan_id`.

*Альтернатива:* выбирать план на клиенте и всегда слать `plan_id`. Отклонено: клиент держит недели только активного плана, а офлайн-очередь отправляет пробежку позже, когда набор планов уже мог измениться.

*Альтернатива:* диапазон из карточки (`plan_start`..`race_date`). Отклонено: у многих планов даты заданы подписями строк, а не карточкой. Окна недель — тот же источник истины, что у план/факта и метки «Нед N».

### 3. Пункты списка «План» в форме
Значения: `"auto"` → ключ `plan_id` не кладётся; `"none"` → `plan_id: null`; иначе id плана. Это значения только UI-контрола, в API они не уходят. Для новой пробежки по умолчанию выбран `auto`. При правке (`fillRunForm`) выбирается `run.plan_id`, либо `none`, если его нет или план не в списке. Пункт «Авто» при правке остаётся и означает «не менять привязку», потому что ключ не уходит. Список виден всегда.

### 4. Область `'none'` в журнале и аналитике
`runScope` получает третье значение `'none'`. `scopedRuns()` фильтрует `r.plan_id == null`. Кнопка «Без плана» добавляется в оба блока `.scope-btn` в `index.html`. `renderCharts` строит область `'none'` как `'all'` (`weeks = null`, без плановых столбцов). `renderLog` показывает название плана только для `'all'` и пустое сообщение для `'none'`. Метка «Нед N» передаётся в `runItemHtml` только при `r.plan_id === activePlanId()`.

## Risks / Trade-offs

- [Лишние чтения GCS при создании пробежки: недели каждого неархивного плана] → читаем только для новой пробежки без явного `plan_id`, а планов у спортсмена единицы. Если станет заметно, можно кешировать диапазон в реестре планов.
- [Смена поведения API: пробежка после окончания активного плана больше не попадает в него] → это и есть цель #71. Спортсмен может выбрать план явно в форме.
- [Пробежка, созданная в «Авто» до того, как у плана появились даты, останется без плана] → её можно перепривязать правкой. Массовая перепривязка вне объёма.
- [Метрика «неделя N из M» и недельный график в областях «все»/«без плана» по-прежнему опираются на недели активного плана и захардкоженный старт] → известное ограничение, календарная аналитика вне объёма (см. proposal.md).

## Migration Plan

Миграции данных нет. Деплой бэкенда и фронтенда идёт одним коммитом в `Dev`. Откат — revert коммита: пробежки с `plan_id: null` уже допустимы старым кодом.
