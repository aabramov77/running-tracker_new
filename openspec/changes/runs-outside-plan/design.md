# Design

## Context

Сейчас поведение такое (мотивация — в proposal.md):

- `clean_run` (`storage.py`) превращает и отсутствующий `plan_id`, и `null`/`""` в `None`. `save_run` подставляет на место `None` прежний план (правка) или `default_plan_id`, а `h_runs_post` (`api.py`) передаёт туда активный план. Различить «по умолчанию» и «без плана» на сервере нельзя.
- Окна недель плана уже умеет считать `compliance.week_windows(weeks, plan_start)`. Признак датированности даёт `compliance.anchor_source(...)`: `DEFAULT` значит «план не датирован», в `storage.py` эта константа импортирована как `UNDATED`. `find_plan` ищет по всему реестру, включая архивные планы, `active_plans(index)` — только неархивные.
- Фронтенд, форма: список `f-plan` заполняется только неархивными планами (`livePlans()`), скрыт, если планов нет, и по умолчанию стоит на активном плане. `saveRun` кладёт `plan_id` только при непустом значении. `clearRunForm` и `endRunEdit` список не трогают, а `renderPlanSelectors` при перестройке сохраняет прежний выбор. Правка пробежки архивного плана сейчас оставляет в списке активный план и перепривязывает пробежку к нему.
- Фронтенд, журнал и аналитика: область — `runScope` (`'plan' | 'all'`), фильтр — `scopedRuns()`. Кнопки `.scope-btn[data-scope]` есть в двух местах `index.html` (журнал и аналитика) и синхронизируются в `setRunScope`. Метку «Нед N» считает `getWeekLabel(date)` по окнам активного плана для любой пробежки — в журнале (`renderLog`) и в последних пробежках на экране «Сегодня». Недельный график раскладывает пробежки по тем же окнам (`weekBuckets`).
- Пробежка, сохранённая без связи, кладётся только в локальный журнал: `loadRunsFromCloud` затем заменяет `runs` ответом сервера, повторной отправки нет.

## Goals / Non-Goals

**Goals:**
- Сервер сам решает привязку по дате, и клиенту не нужно знать недели других планов.
- Контракт API обратно совместим по форме: те же поля, `plan_id: null` уже был допустимым значением в версии пробежки.

**Non-Goals:**
- Не трогаем расчёт план/факт (`plan-compliance`): факт по-прежнему считается по пробежкам, привязанным к плану.
- Не пересчитываем привязку существующих пробежек и не меняем её при правке даты пробежки: при правке без ключа `plan_id` привязка сохраняется, как раньше.

## Decisions

### 1. «Без плана» = ключ `plan_id` есть со значением `null`/`""`; «по умолчанию» = ключа нет
Отдельного флага нет: признак переносится самим отсутствием ключа. `clean_run` кладёт `plan_id` в результат, только если ключ был в теле (`null`/`""` → `None`, id плана → id). `h_runs_post` переносит в `run` только присутствующие поля. `save_run` применяет умолчание, только если ключа `plan_id` в `run` нет: при правке — прежний план, у новой пробежки — `default_plan(day)`. Явный `None` записывается как есть. `_snapshot` и так копирует только пришедшие поля, но проверку `snapshot.get("plan_id") is None` нужно заменить проверкой наличия ключа, иначе явный `None` снова превратится в умолчание.

*Альтернатива:* отдельное строковое значение-маркер (`"none"`). Отклонено: это смешивает идентификатор плана со служебным значением, а `null` в JSON и так означает «нет плана». Риск, что старый клиент шлёт `plan_id: ""`, имея в виду «по умолчанию», проверен: текущий фронтенд при пустом выборе ключ не кладёт (`if (planSel && planSel.value)`). Android-клиент `plan_id` не шлёт.

### 2. Привязка по дате считается на сервере при создании
Новая функция `plan_for_date(bucket, sub, index, day)` в `storage.py`:
1. Берёт все планы реестра, включая архивные: без плана остаётся только пробежка, в дату которой нет никакого плана.
2. Для каждого читает недели (`read_plan_weeks`) и пропускает пустые и недатированные (`anchor_source(...) == UNDATED`).
3. Считает диапазон `[первое окно.start, последнее окно.end]` через `week_windows(weeks, plan.plan_start)`.
4. Из подходящих планов выбирает активный, иначе план с самым поздним началом диапазона.
5. Если не подошёл ни один, а у активного плана диапазон неизвестен (недель нет или они не датированы), возвращает активный план: где он кончается, неизвестно, и прежнее поведение безопаснее. Иначе — `None`.

Совпадение по дате важнее запасного активного плана: у датированного плана диапазон известен точно.

`h_runs_post` передаёт в `save_run` функцию `default_plan(day)`, которая вызывает `plan_for_date`. Параметр `default_plan_id` заменяется на неё. `save_run` вызывает функцию только для новой пробежки (`prev is None`) без ключа `plan_id`, поэтому при правке недели планов не читаются. Тесты, которые передают `default_plan_id` (`test_entity_history.py`), переходят на функцию.

*Альтернатива:* выбирать план на клиенте и всегда слать `plan_id`. Отклонено: клиент держит недели только активного плана, а правило в одном месте на сервере одинаково работает для любого клиента.

*Альтернатива:* диапазон из карточки (`plan_start`..`race_date`). Отклонено: у многих планов даты заданы подписями строк, а не карточкой. Окна недель — тот же источник истины, что у план/факта и метки «Нед N».

### 3. Список «План» в форме
Значения: `"auto"` → ключ `plan_id` не кладётся; `"none"` → `plan_id: null`; иначе id плана. Это значения только UI-контрола, в API они не уходят. Список виден всегда. Строит его одна функция `renderPlanSelectors` с учётом режима формы:
- **новая пробежка:** «Авто (по дате)», «Без плана», неархивные планы; выбран `auto`;
- **правка** (`runEdit` хранит `plan_id` пробежки): «Без плана», неархивные планы и, если пробежка из архивного плана, этот план с пометкой «(архив)». Пункта «Авто» нет: при правке он означал бы «не менять», а подпись «по дате» обещает перепривязку. Выбран план пробежки или `none`.

Архивный план нужен в списке правки, чтобы правка заметки не отвязала пробежку: сервер принимает id архивного плана, потому что `find_plan` ищет по всему реестру.

При перестройке списка (например, после `loadPlans` во время правки) прежний выбор сохраняется, если такой пункт ещё есть. После сохранения новой пробежки (`clearRunForm`) и при выходе из правки (`endRunEdit`) выбор возвращается к `auto`.

### 4. Область `'none'` в журнале и аналитике
`runScope` получает третье значение `'none'`. `scopedRuns()` фильтрует `r.plan_id == null`. Кнопка «Без плана» добавляется в оба блока `.scope-btn` в `index.html`.

`renderCharts` в области `'none'` скрывает карточку недельного объёма. `weekBuckets` раскладывает пробежки по окнам активного плана, а пробежки этой области почти все вне них, и график показал бы нули. Карточке нужен id (`week-chart-card`). Показывать её при возврате в другую область нужно до создания графика: Chart.js в скрытом контейнере получает нулевой размер. Метрики (число, километры, лучший темп) и график темпа считаются по `scopedRuns()`.

`renderLog` показывает название плана только для `'all'` и пустое сообщение для `'none'`. Метку «Нед N» считает `getWeekLabel(run)`: метка пустая, если `run.plan_id !== activePlanId()`. Так она совпадает в журнале и в последних пробежках на экране «Сегодня».

### 5. ИИ-тренер: пробежки вне плана в контексте и в разборе
Сейчас `build_llm_context` берёт в «14 последних тренировок» только пробежки активного плана, если он есть, а `build_run_focus` у пробежки без `plan_id` ищет день в активном плане (запасной путь для пробежек до #25). После привязки по дате оба поведения стали ошибкой. Пробежки после окончания активного плана сохраняются без плана и пропали бы из «последних»: модель решила бы, что спортсмен не бегал. А пробежку, которую спортсмен явно отметил «Без плана», модель сравнивала бы с задачей дня активного плана.

- `build_llm_context`: 14 последних — по всем нескрытым пробежкам. У каждой пометка плана: «текущий план», «без плана» или название плана через `plan_label`. В промпте она стоит в квадратных скобках в строке пробежки. Эвристики (средний темп, тяжёлые, километры за 14) считаются по тем же пробежкам: они описывают организм, а не план, как и нагрузка.
- `build_run_focus`: день плана ищется только в плане самой пробежки. У пробежки без плана — признак `unplanned`, и `format_run_focus` пишет, что пробежка вне плана и сравнивать её с планом не нужно. Запасной путь через активный план больше не нужен: пробежки до #25 при переносе одиночного плана получили его `plan_id` (`migrate_single_plan`).

*Альтернатива:* оставить «последние» по активному плану и добавить отдельный блок «пробежки вне плана». Отклонено: модель видела бы два списка с пересекающимися датами, а порядок «сначала свежие» терялся.

## Risks / Trade-offs

- [Лишние чтения GCS при создании пробежки: недели каждого плана, включая архивные] → читаем только для новой пробежки без ключа `plan_id`, а планов у спортсмена единицы. Если станет заметно, можно кешировать диапазон в реестре планов.
- [Смена поведения API: пробежка после окончания активного плана больше не попадает в него] → это и есть цель #71. Спортсмен может выбрать план явно в форме.
- [Пробежка, попавшая по дате в архивный план, видна только в области «Все», с названием этого плана] → так решено: без плана остаётся только пробежка, в дату которой нет никакого плана. Перепривязать можно правкой.
- [Пробежка, привязанная к активному плану, пока у него не было дат, останется в нём, даже если после датирования её дата окажется вне его недель] → её можно перепривязать правкой. Массовая перепривязка вне объёма.
- [Метрика «неделя N из M» и недельный график в области «все» по-прежнему опираются на недели активного плана и захардкоженный старт] → известное ограничение, календарная аналитика вне объёма (см. proposal.md). В области «без плана» недельный график скрыт.
- [Пробежка, сохранённая без связи в «Авто», до перезагрузки журнала видна в «Без плана», а не в «Текущий план»] → на сервер такая пробежка не уходит и сейчас. Это отдельная проблема, вне объёма.
- [В «14 последних» у ИИ-тренера теперь могут быть пробежки других планов и вне плана, и меньше пробежек текущего плана] → выполнение плана модель получает отдельным блоком по всем пробежкам плана, а пометка в строке говорит, к какому плану относится пробежка.

## Migration Plan

Миграции данных нет. Деплой бэкенда и фронтенда идёт одним коммитом в `Dev`. Откат — revert коммита: пробежки с `plan_id: null` уже допустимы старым кодом.
